## 2. `Harness` 在系统里做什么

本文把 `Harness` 理解为包围模型的运行机制：组织输入与上下文，调用模型，执行工具，处理返回值，并控制何时继续、等待或结束。

可以用下面的过程理解，而不把它当作七个项目完全相同的内部实现：

```text
用户目标
  ↓
整理指令、历史和资料
  ↓
调用模型 → 返回最终结果 → 验收
  ↓ 需要行动
检查权限 → 执行工具 → 记录结果
  ↓
更新状态与上下文 → 继续调用模型
```

模型负责生成推理结果或行动请求，运行机制负责把行动落实到环境中。工具能否重复执行、进程中断后怎么恢复、长结果怎么处理，都需要具体实现。

这七项也不处在完全相同的产品层次：有的是可嵌入程序的 `SDK`，有的是可扩展运行框架，有的是带交互界面的编程工具，还有的是长期运行的个人助手。它们之间可能组合使用。

`Claude Agent SDK` 低于本专题的万星门槛，但它是图片指定的比较对象，因此在本文展示；不把它追加计入主榜的 `144` 个项目。

### 3.1 `SDK`、框架与成品的取舍

**已有产品，想嵌入 `Agent` 能力**：先比较 `Claude Agent SDK` 和 `Deep Agents`。前者复用已有运行能力；后者提供可替换的任务执行组件。具体模型、鉴权和部署要求仍需按官方文档核对。

**已有开发任务，想马上使用工具**：先试 `OpenCode`，用一个真实修复任务评估编辑、执行和验证过程。如果目标是深入定制循环与扩展，可进一步研究 `Pi`。

**希望助手进入日常工作渠道**：比较 `OpenClaw` 与 `Hermes Agent`，重点看消息入口、状态、记忆和后台运行方式。这里增加的是系统运行与使用方式的需求，不能只靠一个模型调用接口满足。

**关注插件化架构本身**：研究 `DeepSeek Harness`，同时考虑预览阶段的接口变化成本。官方明确提示可能发生不兼容变更，星数不能消除这一限制。[官方说明](https://github.com/deepseek-ai/deepseek-harness#developer-preview)。

## 4. 比功能打勾更有用的四组问题

### 4.1 上下文、状态和记忆分别存什么

| 概念 | 需要解决的问题 | 验证方法 |
| --- | --- | --- |
| 当前上下文 | 这次模型调用能看到哪些信息 | 加入超长工具结果，检查保留、摘要和丢弃的内容 |
| 执行状态 | 任务走到哪一步，等待什么 | 中断进程后恢复，检查是否重复执行已完成步骤 |
| 长期记忆 | 跨任务保留哪些事实或经验 | 新建会话，验证能否正确找回信息，以及能否删除或纠正 |

`Deep Agents` 官方列出长会话摘要、工具结果写入磁盘和可插拔记忆后端；`Hermes Agent` 强调历史会话检索与技能积累。这些是不同机制，不能简单归成一个“支持记忆”的复选框。[Deep Agents](https://github.com/langchain-ai/deepagents#readme)、[Hermes Agent](https://github.com/NousResearch/hermes-agent#readme)。

### 4.2 多 `Agent` 是内置行为，还是扩展方式

`Deep Agents` 明确提供上下文隔离的子 `Agent`；`OpenCode` 内置通用子 `Agent`；`Pi` 官方说明默认不包含子 `Agent` 和计划模式，需要通过扩展或包实现所需工作方式。因此，不能仅凭截图底部出现“多 `Agent`”，就推断七者默认具有同样的协作能力。[Deep Agents](https://github.com/langchain-ai/deepagents#readme)、[OpenCode](https://github.com/anomalyco/opencode#agents)、[Pi](https://github.com/earendil-works/pi#readme)。

实际试用时检查：子任务拿到哪些上下文、结果如何返回、失败由谁重试、多个任务是否会修改同一个文件。角色数量本身不说明协作是否有效。

### 4.3 扩展点允许你改到哪一层

- `Claude Agent SDK`：重点读工具接入、权限回调和应用调用接口。
- `Deep Agents`：重点读文件后端、工具与子 `Agent` 的替换方式。
- `Pi`：重点读扩展、技能、包和程序调用入口。
- `DeepSeek Harness`：重点读插件依赖、生命周期与组合机制。

这些是依据各自官方公开接口整理的阅读方向，不代表其他项目不能扩展。先确定需要改哪层，再判断是否需要修改上游源码。

### 4.4 工具可用与工具获准执行是两回事

`Claude Agent SDK` 当前文档明确：`allowed_tools` 是自动批准名单，不会把其他工具从工具集中删除；阻止特定工具需要使用相应禁止配置，未列出的工具还会进入权限判断。[官方工具与权限说明](https://github.com/anthropics/claude-agent-sdk-python#using-tools)。

同样，某个项目标注“支持工具调用”，并没有回答谁有权执行、工作目录在哪里、失败是否可重试、操作是否可撤销。做选型时应验证这些实际行为。

## 5. 针对这个博客，怎么开始

建议用一个小任务比较两个候选：**读取指定 `GitHub` 仓库，生成带来源、星数和日期的中文项目卡片。**

1. 用普通程序获取仓库元数据，名称、星数、归档状态保持接口原值。
2. 用模型辅助理解官方说明，输出项目定位与分类依据。
3. 将结果保存为待审稿，人工核对后再进入文章目录。
4. 测试仓库不存在、请求失败、资料太长和任务中断这几种情况。

如果想把这个能力做进自己的服务，先比较 `Claude Agent SDK` 与 `Deep Agents`；如果想研究运行机制，读 `Pi`；如果只是希望工具协助维护博客，先用已有编程助手完成一次可验收的改动。只有需要聊天渠道或跨任务记忆时，再评估个人助手系统。

最终选型记录至少写清：**完成率、调用成本、需要人工接手的位置、失败后能否恢复、以后怎样替换组件**。两张图适合帮助建立项目地图，具体决定需要来自你自己的任务验证。
