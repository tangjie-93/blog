`AI Coding` 的有效用法是让模型参与可验证的工程流程，而不是把整个需求一次性交给它。人负责目标、边界和取舍，工具负责搜索、草拟、转换和检查。

## 一、一个可复用的工作流

1. **理解仓库**：先读取项目约定、入口、调用方和测试，再描述要改的范围。
2. **拆小任务**：一次只处理一个行为，明确输入、输出和验收条件。
3. **让模型先分析**：列出影响文件、风险和最小方案，确认后再修改。
4. **小步实现**：每次改动保持可读、可回滚，避免顺手重构无关代码。
5. **运行验证**：执行格式化、类型检查、单元测试和构建。
6. **审查差异**：检查未请求的文件、敏感信息、边界条件和兼容性。

## 二、提示词应该包含什么

- 背景：项目使用的框架、运行方式和已有约定。
- 目标：要改变的用户行为。
- 范围：允许修改的文件或模块。
- 约束：兼容性、性能、安全和禁止引入的依赖。
- 验收：可观察的结果和需要运行的命令。

```text
请只修改 src/services/search.ts。
目标：搜索为空时返回空列表，不发起请求。
约束：保留现有错误处理，不新增依赖。
验收：补充一个空输入测试，并运行 pnpm test。
```

## 三、哪些事情不要交给模型决定

- 权限、密钥、支付和数据删除等高风险操作。
- 未经验证的依赖升级、数据库迁移和部署发布。
- 没有业务上下文的架构重构。
- 只看局部代码就下结论的安全问题。

涉及外部系统时，使用最小权限、人工确认和可回滚步骤。模型生成的代码必须经过同样的测试、审查和监控。

## 四、衡量是否真的提速

记录从需求到合并的时间、返工次数、缺陷数量和审查发现的问题。若生成代码让审查和修复成本增加，说明上下文、任务拆分或验收标准还不够清楚。

好的 `AI Coding` 不是少写代码，而是更快得到一份经过验证、团队敢于维护的代码。
