# 05. `RAG` 与知识库

这篇文章保留在 `AI` 总路线中，负责回答“`RAG` 解决什么问题、应该怎样学习”。具体实现已经集中到 [RAG 专题](../rag/)，避免同一套内容在两个入口重复维护。

## 1、先建立正确的心智模型

`RAG` 不是把文档上传到向量库后让模型“自动学会”。它是一条可追溯的证据链：

```text
文档 → 解析/OCR → 清洗 → 结构化切分 → Embedding/关键词索引
问题 → 权限与时间过滤 → 召回 → 重排 → Context → 回答/引用/拒答
```

需要区分四个概念：

- `LLM` 负责理解问题和组织语言，不保证掌握最新业务事实。
- 知识库保存外部事实，必须有来源、版本、生效时间和权限。
- `chunk` 是检索和引用的最小证据单元，应保留标题路径与页码。
- `Embedding` 把文本映射成向量，适合找语义相近的表达，不能代替权限和事实校验。

每个阶段都要回答四个问题：输入是什么，输出是什么，失败如何观测，谁对结果负责。只会调用框架接口，无法定位“召回错、重排错还是生成错”。

## 3、两条学习路线

### 3.1 先跑再拆

适合第一次接触 `RAG`：先运行 [05 最小实战](../rag/05-最小实战.md)，看到一次带引用的回答，再回到 01–04 解释每个中间结果，最后用 06–07 做评估和生产审查。

### 3.2 先学系统再写代码

适合要负责生产系统的人：按 01→02→03→04→05 顺序学习，重点记录 `chunk`、检索命中、证据和最终回答之间的字段变化，再进入 06–08。

## 4、什么时候不用 `RAG`

需要完整集合、精确聚合、事务一致性或权限写入的请求，应使用数据库和工作流。`RAG` 可以解释制度，却不能替代 `SQL`、审批和业务规则引擎。
