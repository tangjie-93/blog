# 05. `RAG` 与知识库

如果你第一次看到 `RAG`，可以先把它理解成“让模型开卷考试”。

模型负责理解问题和组织语言，知识库负责提供本次回答允许使用的材料。用户问“工作满一年有几天年假？”时，系统不会只依赖模型训练时记住的常识，而是先找出公司的请假制度，再让模型根据这段制度回答，并把来源展示出来。

`RAG` 的英文是 `Retrieval-Augmented Generation`，意思是“检索增强生成”：

- Retrieval：从外部资料中检索相关内容。
- Augmented：把检索结果补充到模型上下文。
- Generation：让模型根据上下文生成答案。

它解决的是“模型需要使用会更新的外部知识”这个问题。它不能替代数据库查询、权限系统、审批流程，也不能保证模型永远不犯错。

## 1. 先分清四个基本概念

### 1.1 什么是 `LLM`

`LLM`（大语言模型）擅长总结、改写、解释和对话，但不会自动知道你的私有文档，也不能凭空获得刚刚发布的制度。模型参数里的知识需要重新训练或微调才能更新；公司的制度、产品说明和合同应该放在可更新、可检索的知识库里。

### 1.2 什么是知识库

知识库不是一个特定的数据库产品，而是一组经过整理、切分、索引的资料。资料可以来自 `Markdown`、网页、`PDF`、`Word`、数据库记录、工单、图片和内部 `API`。

知识库真正有用的前提，是每段内容都能回答“来自哪份文档、哪一版、哪一页、何时生效、谁有权限看”。

### 1.3 什么是 `chunk`

整篇文档通常太长，不能每次都全部交给模型，所以要先切成较小的片段。每个片段就是一个 `chunk`。

```text
原文：《员工手册》第三章
  -> chunk 1：年假定义和适用范围
  -> chunk 2：工作满一年后的年假天数
  -> chunk 3：年假的申请和结转规则
```

切分太大，检索会带回很多无关内容；切分太小，条件和例外可能被拆开。好的 `chunk` 应该表达一个完整的小主题，并保留标题路径。

### 1.4 什么是 `Embedding`

`Embedding` 模型把文字转换成一串数字，也叫向量。语义相近的文字通常距离更近：

```text
“工作满一年有几天年假？”
“入职一年后可以休多少天年假？”
```

两句话字面不同，但意思相近，向量检索有机会把同一段制度找出来。向量相近只是“可能相关”，不是事实正确；最终仍然要看原文和引用。

## 2. 一张图看懂完整链路

`RAG` 有两条链路：离线链路负责把资料准备好，在线链路负责回答一次具体问题。

```text
离线链路（文档更新时执行）
原始文档
  -> 解析/OCR
  -> 清洗和去重
  -> 按结构切分 chunk
  -> 保存 metadata
  -> 生成 embedding
  -> 建立向量/关键词索引

在线链路（用户提问时执行）
用户问题
  -> 问题标准化
  -> 权限、租户、时间过滤
  -> dense 向量召回 + BM25 关键词召回
  -> 合并候选并 rerank
  -> 拼接带编号的 context
  -> LLM 根据证据生成答案
  -> 返回引用，证据不足则拒答
```

可以把它想成图书馆：

| `RAG` 部件 | 图书馆类比 | 输入 | 输出 |
| --- | --- | --- | --- |
| `Loader` | 把书搬进馆 | 文件、网页、数据库记录 | 原始文本和基础信息 |
| 解析/`OCR` | 把书读出来 | `PDF`、图片、表格 | 可搜索的文字结构 |
| `Text Splitter` | 给书分章节 | 长文档 | 多个 `chunk` |
| `Embedding` | 给内容做语义编码 | `chunk` 文本 | 向量 |
| 向量库 | 语义索引 | 向量和 `metadata` | 可查询的索引 |
| `BM25` | 关键词目录 | 词语和出现次数 | 关键词候选 |
| `Retriever` | 根据问题找书 | 问题和过滤条件 | 候选片段 |
| `Reranker` | 馆员重新挑选 | 候选片段和问题 | 排好顺序的证据 |
| `Prompt` | 给答题者的规则 | 问题、证据、约束 | 模型上下文 |
| `LLM` | 根据材料作答 | 上下文 | 自然语言答案 |
| 引用 | 书籍页码 | 来源 `metadata` | 可核验的位置 |

## 3. 离线链路：把原始资料变成知识

### 3.1 加载和解析

`Loader` 从 `Markdown`、`HTML`、`PDF`、`Word`、网页或数据库读取内容。解析阶段检查正文完整、标题保留、页码可回溯、表格行列没有错位，扫描版 `PDF` 是否经过 `OCR`。

原文中的“上限为 5000 元”如果被 `OCR` 读成“500 元”，后面所有检索和回答都会围绕错误事实进行。双栏 `PDF` 顺序错乱、页眉页脚重复、图片文字没有提取，都是数据摄取阶段的问题。

### 3.2 清洗、去重和 `metadata`

清洗可以去掉重复页眉页脚、空白段落、导航菜单和完全重复的文档，但不能删掉标题、例外条件、生效日期和脚注。

文档更新时应保留：

```json
{
  "document_id": "leave-policy",
  "source": "hr/leave-policy.md",
  "version": "2026-10-01",
  "effective_from": "2026-10-01",
  "content_hash": "sha256:...",
  "acl": ["all-employees"]
}
```

`metadata` 是每段内容的身份证，决定引用、版本过滤、权限过滤、旧索引删除和审计是否可做。

### 3.3 切分 `chunk`

常见参数如下：

| 参数 | 解释 | 失败表现 |
| --- | --- | --- |
| `chunk_size` | 每块最多多长 | 太大召回粗，太小语义不完整 |
| `chunk_overlap` | 相邻块重复多少 | 太小边界断裂，太大重复和成本增加 |
| `separator` | 优先在哪里断开 | 硬截断会切开标题和条件 |

制度类文档应保留“第几章/第几条”的标题路径；表格最好按行或业务记录切分。没有适合所有文档的固定数字，应使用真实问题测试正确片段是否被召回。

### 3.4 建立索引

只用向量检索可能漏掉订单号、条款编号和产品型号；只用关键词又可能理解不了同义表达。生产系统常把两路结果合并：

- Dense 检索：用 `Embedding` 找语义相似片段。
- `BM25` 检索：用关键词出现频率找精确匹配。
- Hybrid 检索：合并两路候选，常用 `RRF` 融合排名。
- `Reranker`：对少量候选再做精细相关性判断。

本文的最小 Demo 只实现本地 `dense` 余弦相似度检索，未实现 `BM25`、`RRF`、`Reranker`、ACL 和版本过滤，不能当作生产方案。

## 4. 在线链路：一次问题怎样变成答案

### 4.1 问题标准化

用户可能只问“这个能报多少？”。系统可以结合会话历史改写成“员工工作餐每月可以报销的最高金额是多少？”。改写的目标是便于检索，不能改变原意；编号、金额、日期等精确字段必须保留。

### 4.2 权限和时间过滤

检索前根据用户身份、租户、部门和文档生效时间过滤候选：

```text
tenant_id = 当前租户
acl 包含 当前用户
effective_from <= 当前时间
effective_to 为空或 > 当前时间
```

权限必须在检索层生效，不能先把秘密资料召回，再要求模型不要说。答案缓存和向量缓存也不能跨用户泄露内容。

### 4.3 召回和重排

`Retriever` 先找一批可能相关的片段，不直接决定最终答案。`top_k` 太小会漏掉正确条款，太大则会增加延迟并淹没证据。

如果正确片段排在第 8 位，依次检查原文解析、`chunk` 边界、关键词/向量召回、版本过滤和 `rerank`er 排序。只有正确证据已经进入上下文，才检查提示词和生成模型。

### 4.4 组织 `context`

每条证据都应带编号和出处：

```text
[E1] 来源：hr/leave-policy.md
版本：2026-10-01，章节：年假
员工工作满一年后，每年享有 5 天年假。

[E2] 来源：hr/leave-policy.md
版本：2026-10-01，章节：申请
年假应在当年使用，跨年结转需要额外审批。
```

这样模型可以引用 [E1]，用户也能回原文核对。上下文还要去重、排序并控制长度，召回越多不代表答案越可靠。

### 4.5 生成、引用和拒答

提示词要明确：

1. 只根据提供的证据回答；
2. 事实句引用对应的 [E#]；
3. 证据没有答案时明确拒答；
4. 不要编造 `URL`、页码、金额或版本；
5. 把推测和事实分开。

有引用不等于引用支持答案，引用覆盖率、引用段落是否正确、版本是否有效都需要评估。

## 5. 最小 Demo：把概念映射到代码

仓库中的 [本地 `RAG` 实战](../rag/05-最小实战.md) 用本机 `Ollama` 跑通教学链路：

```bash
cd docs/articles/rag/examples
python3 rag_demo.py ingest data /tmp/rag-index.json
python3 rag_demo.py ask /tmp/rag-index.json '午餐补贴是多少？'
python3 rag_demo.py ask /tmp/rag-index.json '访客进入办公区需要什么？' --retrieval-only
python3 -m unittest discover -s tests -v
```

它实际完成了：

1. 读取样例 `Markdown`；
2. 按标题和行切分；
3. 调用 `Ollama` 的 /`api/embed`；
4. 保存文本、来源、标题和向量；
5. 用余弦相似度做 `dense` 召回；
6. 给证据编号；
7. 调用 /`api/chat` 生成回答；
8. 分数低于阈值时拒答。

运行前需要本机启动 `Ollama`，并准备 `embeddinggemma` 和 `qwen3:4b`，也可以通过参数替换模型。Demo 使用 `JSON` 和线性扫描，适合观察每一步，不适合百万文档、多人并发或敏感数据。它没有 `BM25`、ACL、版本过滤和生产级持久化。

`--retrieval-only` 只打印召回结果：若没有正确证据，先修数据和检索；若有正确证据而完整问答仍错，再检查提示词、上下文长度和模型输出。

## 6. 用评估定位问题

准备固定题集，覆盖精确编号、同义改写、跨段落条件、无答案、旧版与当前版本、权限隔离和提示注入。

常用指标：

- `Recall@k`：正确证据是否出现在前 k 个候选里。
- `MRR`：正确证据平均排得多靠前。
- 引用覆盖率：答案事实是否都有证据。
- `Faithfulness`：答案是否忠实于证据。
- 拒答质量：无证据时是否稳定拒答。
- 延迟和成本：耗时、`token` 数和模型调用次数。

| 现象 | 优先检查 |
| --- | --- |
| `Recall@k` 低 | 解析、清洗、切分、分词、`Embedding`、过滤 |
| 召回正确但答案错 | `Reranker`、上下文预算、提示词、例外条款 |
| 无答案题被回答 | 分数阈值、证据门槛、拒答分支 |
| 旧版或越权内容出现 | 生效时间、ACL、缓存 |
| 引用打不开或版本不对 | `metadata`、文档 ID、索引版本、`URL` |

每次只改变一个变量，并保存题集、索引版本、`Embedding` 模型、切分参数和失败样本。

## 7. 什么时候不该用 `RAG`

`RAG` 适合“根据资料解释和回答”。以下请求通常交给其他系统：

- 统计订单总额：数据库和 `SQL`；
- 创建审批单：业务 `API` 和工作流；
- 返回全部符合条件的记录：可分页、可校验的查询；
- 判断法律责任：专业审核和明确责任边界。

模型不能替代事务一致性、权限校验、精确计算和审批责任。复杂系统可以组合数据库、工作流和 `RAG`，但每个系统仍负责自己的边界。
