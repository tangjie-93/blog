# 项目与资料：对照阅读的开源实现

本专题的很多设计来自对真实项目的观察。这一篇给出**可对照阅读**的仓库、论文与基准，以及怎么读。

> 时间说明：以下信息以 **2026-11** 的公开仓库为准。开源项目迭代很快，接口、目录、许可证都可能变化。使用前请以仓库的 `LICENSE`、`README`、`release` 和实际代码为准。本专题不保证任何第三方项目的当前许可、Star 数或维护状态。
>
> 特别提醒：部分仓库在 `GitHub API` 中返回 `NOASSERTION`（无法识别标准许可证）或未声明许可证。**这类项目不能默认可以商用**，必须逐一确认。

## 1、完整的 `RAG` 应用

### 1.1 `WeKnora`（腾讯）

- 仓库：`https://github.com/Tencent/WeKnora`
- 形态：`Go` 编排 + 独立文档解析服务，支持本地/服务端向量库，带会话与流式问答。
- 适合看：
  - 文档上传 → 解析 → 切分 → 索引 → 检索 → 生成的全链路；
  - 异步任务、状态机、失败重试；
  - `SSE` 流式、停止/恢复；
  - 知识库与租户模型。
- 许可：仓库 `LICENSE` 状态需自行确认（`API` 可能返回 `NOASSERTION`）。
- 本专题 [08 全链路](./08-文档上传到问答全链路.md) 主要以它为参照，但**区分了当前实现与目标设计**，不要把它当成唯一标准答案。

### 1.2 `RAGFlow`

- 仓库：`https://github.com/infiniflow/ragflow`
- 形态：深度文档理解 + 可视化编排，强调解析质量与可追溯引用。
- 适合看：
  - 复杂 `PDF`/表格的解析流水线；
  - 切片模板与可视化调试；
  - 检索与引用的产品化呈现。
- 许可：`Apache-2.0`（以仓库为准）。

### 1.3 `Dify`

- 仓库：`https://github.com/langgenius/dify`
- 形态：`LLM` 应用平台，内置知识库、工作流、`Agent`。
- 适合看：
  - 知识库产品化：分段、召回测试、命中测试；
  - 工作流编排；
  - 多模型接入与插件体系。
- 许可：`API` 可能返回 `NOASSERTION`，使用前确认仓库 `LICENSE` 与附加条款。

### 1.4 `FastGPT`

- 仓库：`https://github.com/labring/FastGPT`
- 形态：知识库问答 + 工作流，中文社区活跃。
- 适合看：
  - 知识库训练/索引流程；
  - 混合检索与重排配置；
  - 引用与对话产品化。
- 许可：需以仓库为准。

| 项目 | 仓库 | 特点 |
| --- | --- | --- |
| `Qdrant` | `https://github.com/qdrant/qdrant` | `Rust`，过滤与混合检索能力强，`Apache-2.0` |
| `Milvus` | `https://github.com/milvus-io/milvus` | 分布式、大规模，生态完整 |
| `Weaviate` | `https://github.com/weaviate/weaviate` | 内置混合检索与模块化向量化 |

| `Chroma` | `https://github.com/chroma-core/chroma` | 轻量、开发体验好 |
| `FAISS` | `https://github.com/facebookresearch/faiss` | 向量检索库，不是数据库 |
| `Elasticsearch` / `OpenSearch` | 官方仓库 | `BM25` + 向量，日志/搜索场景成熟 |

选型不要只看基准测试的 `QPS`。要看：

- 过滤能力（权限、租户、时间）；
- 混合检索；
- 更新/删除；
- 备份与运维；
- 成本与团队熟悉度。

## 8、怎么读一个开源 `RAG` 项目

不要从 `main.go` 或 `app.py` 开始逐行读。按数据流找入口：

```text
1. 上传接口：文件怎么存、返回什么、是否异步
2. 任务表/队列：状态字段、重试、幂等
3. 解析服务：输入输出格式、错误处理
4. 切分：策略、参数、元数据
5. 嵌入：批大小、重试、模型配置
6. 索引：写入、删除、版本
7. 检索：多路、融合、过滤
8. 重排：候选数、阈值、降级
9. 组装：证据格式、预算
10. 生成：提示词、流式、引用
11. 持久化：消息、引用、完成信号
12. 测试：失败路径覆盖了哪些
```

读的时候带着问题：

- 失败时状态是什么？
- 重复执行会怎样？
- 删除/更新怎么传播？
- 权限在哪里过滤？
- 超时和重试怎么设置？
- 哪些是“当前实现”，哪些是“文档里的目标设计”？

## 10、资料使用建议

1. **先跑再读**：先让一个最小系统跑起来，再看框架源码；
2. **对照读**：同一个环节看两个项目怎么实现，差异往往就是设计取舍；
3. **看测试**：测试比 `README` 更能说明边界条件；
4. **看提交历史**：最近的修复往往暴露真实坑；
5. **不迷信架构图**：以代码和数据流为准；
6. **记录版本**：今天读到的行为，下个版本可能就变了。

## 11、检查清单

- [ ] 选定的开源项目已确认许可证与商用条件；
- [ ] 知道它的索引/检索/生成入口在哪；
- [ ] 读过失败路径与测试；
- [ ] 用自有文档验证过解析质量；
- [ ] 用自有评估集验证过检索与生成；
- [ ] 记录了版本与配置；
- [ ] 有替代方案，避免被单一项目锁死。

## 12、一句话总结

开源项目最好的用法不是“部署一个”，而是**把它当成一份可执行的架构文档**：对照数据流读，带着失败问题读，最后用自己的评估集判断它是否适合你的场景。
