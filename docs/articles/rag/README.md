# `RAG` 专题：从一句话到可运维的知识问答

这个专题只回答一个问题：**当模型不知道你公司的文档时，怎样让它基于文档回答，并且答得对、说得出出处、答不出时敢说不知道。**

它分成三层：

1. **能用大白话讲清楚**：不写代码的人读完 [01 白话 `RAG`](./01-白话RAG.md)，也能说明白 `RAG` 是什么、解决什么问题、什么时候没用。
2. **能自己写出来**：跟着 [03 最小实现](./03-最小实现.md) 跑通一个不到 200 行、零依赖的版本，再逐层替换成生产组件。
3. **能解释故障并上线**：用 [08 全链路](./08-文档上传到问答全链路.md)、[09 评估](./09-评估.md)、[10 生产化](./10-生产化.md)、[12 排障手册](./12-排障手册.md) 把 Demo 变成可运维系统。

## 2、一张总图

```text
离线（文档进来）                         在线（问题进来）
─────────────────────────────────       ─────────────────────────────────
上传 → 解析 → 清洗 → 切块              提问 → 理解/改写 → 召回
     → 向量化/关键词 → 建索引                → 融合 → 重排 → 组装证据
     → 状态收敛 → 可检索                     → 拼 Prompt → 流式生成 → 引用/拒答
```

两条链路通过一份**持久化的索引**衔接，而不是通过内存或一次请求衔接。这决定了三件事：

- 文档处理必须是异步任务，必须有状态、重试和幂等；
- 索引必须带版本、来源、权限和删除能力；
- 问答失败时要能判断是“文档没进来”“没检索到”还是“模型没用好证据”。

## 3、统一的数据契约

全专题使用同一组对象。调试时沿着 `chunk → hit → evidence → answer` 追，而不是盯着最终那段文字猜：

| 对象 | 关键字段 | 谁产生 | 下一步检查什么 |
| --- | --- | --- | --- |
| `chunk` | `chunk_id`、正文、标题路径、页码/坐标、版本、`ACL`、内容哈希 | 摄取 | 能否回到原文？能否按权限过滤？ |
| `hit` | `chunk_id`、召回通道、原始分、排名、过滤原因 | 检索/融合 | 正确证据有没有进候选集？ |
| `evidence` | `chunk_id`、引用文本、来源位置、版本 | 上下文组装 | 每个结论是否有真实来源？ |
| `answer` | 文本、引用列表、拒答原因、`run_id` | 生成 | 是否只依据证据？能否审计复现？ |

一句话：**答案错，先问“对的片段进没进候选”，再问“模型有没有用对证据”。** 这一步能把数据问题、检索问题和生成问题分开。

## 5、示例代码

[`examples/rag_demo.py`](./examples/rag_demo.py) 是本专题的基线：

- 只用 `Python` 标准库，通过 `HTTP` 调本机 `Ollama`；
- `ingest` 把 `Markdown` 切成片段、算向量、原子写入 `JSON` 索引；
- `ask` 做余弦召回、阈值过滤、编号证据、带引用回答，证据不足时拒答；
- 自带单元测试，用假客户端隔离网络。

```bash
cd docs/articles/rag/examples
python3 -m unittest discover -s tests -v
python3 rag_demo.py ingest data index.json
python3 rag_demo.py ask index.json "午餐补贴是多少"
```

[03 最小实现](./03-最小实现.md) 会逐段解释它；[04](./04-数据摄取.md) 到 [07](./07-生成与引用.md) 则说明每一段在生产环境要换成什么。

## 7、一句话总结

`RAG` 不是“把文档塞给模型”，而是**建一套可追溯的证据供应链**：文档进得来、切得好、找得到、排得准、用得对、说得清、错得了可查。
