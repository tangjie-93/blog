# `RAG` 专题：从一句话到可运维的知识问答

这个专题只回答一个问题：**当模型不知道你公司的文档时，怎样让它基于文档回答，并且答得对、说得出出处、答不出时敢说不知道。**

它分成三层：

1. **能用大白话讲清楚**：不写代码的人读完 [01 白话 `RAG`](./01-白话RAG.md)，也能说明白 `RAG` 是什么、解决什么问题、什么时候没用。
2. **能自己写出来**：跟着 [03 最小实现](./03-最小实现.md) 跑通一个三百行左右、零依赖的版本，再逐层替换成生产组件。
3. **能解释故障并上线**：用 [08 全链路](./08-文档上传到问答全链路.md)、[09 评估](./09-评估.md)、[10 生产化](./10-生产化.md)、[12 排障手册](./12-排障手册.md) 把 Demo 变成可运维系统。

## 3、统一的数据契约

### 3.1 先用一句白话解释

所谓**数据契约**，就是各个环节约定好：“我交给下一步的东西里，必须带哪些信息，这些信息是什么意思。”它不是某个框架的专有功能，也不要求所有项目都使用同一套字段名。

比如检索模块不能只返回一句“补贴 30 元”，还要告诉下一步：**这句话出自哪个文档、哪个版本、哪一页，以及当前用户有没有权看。** 否则生成模块即使答对了，也无法给出可靠出处，更无法排查是否用了过期制度。

本专题用四个名字区分这条链上的东西：

| 名字 | 白话理解 | 什么时候出现 | 它不等于什么 |
| --- | --- | --- | --- |
| `chunk`（文档块） | 从原文切下来、存进知识库的一段资料 | 文档摄取时 | 不代表它和当前问题有关 |
| `hit`（检索命中） | 因为这次提问而被检索出来的候选资料 | 每次检索时 | 排名靠前不代表一定能回答 |
| `evidence`（本轮证据） | 从候选里选出、真正交给模型使用的资料 | 组装上下文时 | 不保证模型一定会正确使用 |
| `answer`（回答结果） | 给用户的答案，以及对应引用或拒答说明 | 生成后 | 不是一段无法追溯来源的文字 |

**可以把它理解成：资料库里的卡片 → 本次找到的卡片 → 最终放上答题桌的卡片 → 根据卡片写出的答案。**

### 3.2 跟着一个问题走一遍

假设公司上传了一份虚构的《员工福利制度》，第 3 页写着：

> 公司为工作日加班的员工提供每餐 30 元午餐补贴。

用户提问：“午餐补贴是多少？”下面观察这句话怎样穿过四个环节。

> 以下字段是为了讲清关系而设计的示意结构，不是要求所有字段都直接发送给模型，也不与 [03 最小实现](./03-最小实现.md) 的精简代码逐字段对应。

### 3.3 第一步：`chunk`——先把资料保存好

摄取模块解析文档、切块，并给这段内容保存身份和出处：

```json
{
  "chunk_id": "hr-v2-c003",
  "doc_id": "hr-policy",
  "text": "公司为工作日加班的员工提供每餐 30 元午餐补贴。",
  "heading_path": ["员工福利制度", "午餐补贴"],
  "page": 3,
  "version": "v2",
  "acl": ["employee"]
}
```

这些字段分别解决什么问题？

- **`chunk_id`：这段资料是谁。** 后续命中、证据、引用都靠它关联回来。这里把版本写进 ID 只是示例，不是唯一命名方式。
- **`doc_id`、`heading_path`、`page`：它从哪里来。** 用来回到《员工福利制度》的“午餐补贴”章节、第 3 页。网页或纯文本不一定有页码，可以改用段落锚点、字符偏移等位置。
- **`version`：它是哪一版。** 防止制度更新后，还把旧版补贴当成现行规则。
- **`acl`：谁可以看。** `ACL` 是访问控制列表；这里假设具有 `employee` 身份的用户可访问，实际规则由服务端校验，不能靠模型判断。
- **内容哈希（示例省略）：内容有没有变化。** 可以帮助检测更新或去重，但它不能代替权限检查。

**这时还没有用户提问。** 无论后来问补贴、休假还是差旅，这个块都可以作为知识库里的资料存在。

### 3.4 第二步：`hit`——这次问题找到了哪些候选

用户提问后，检索模块根据问题查索引，返回命中的候选。它在文档块身份之外，增加了“这次是怎么找到它的”的信息：

```json
{
  "chunk_id": "hr-v2-c003",
  "channel": "vector",
  "raw_score": 0.82,
  "rank": 1
}
```

- **`channel`：哪条路找到的。** 这里是向量检索；也可能是关键词检索。同一个块可能被多条通道找到，后续需要融合与去重。
- **`raw_score`：该通道给它的原始分。** 此处 `0.82` 只是示意，**不是“答案有 82% 的正确率”**，不同模型、不同检索通道的原始分也不能直接当成同一种分数比较。
- **`rank`：在这次结果里的位置。** 这里表示该通道排第 1；融合、重排后还可能改变。

`hit` 可能携带正文，也可能先只返回 ID 和分数，再按 ID 读取正文。关键是能通过 `chunk_id` 找回准确的资料及其版本。

**命中只是“值得看看”，不是“已经找到答案”。** 例如“出差餐费报销标准”也可能被搜出来，但它和工作日加班午餐补贴不是同一件事。

权限应尽量在召回前或召回时过滤，最终组装证据前仍要保证授权有效。被过滤原因可以记录在受控的诊断日志里，**不能把无权查看的正文或相关诊断信息交给模型和用户**。

### 3.5 第三步：`evidence`——最终让模型看哪些资料

检索可能找到 20 个候选，但模型不一定都要看。上下文组装模块结合重排结果，去掉重复、无关或过期内容，在上下文长度允许的范围内挑选证据，并给它们编上本轮编号：

```json
{
  "evidence_id": "E1",
  "chunk_id": "hr-v2-c003",
  "quote": "公司为工作日加班的员工提供每餐 30 元午餐补贴。",
  "source": {
    "doc_id": "hr-policy",
    "title": "员工福利制度",
    "page": 3,
    "version": "v2"
  }
}
```

这里多出来的 **`E1` 是本轮问答的引用编号**，方便模型写“依据 [E1]”。它不是数据库里的永久 ID；下一次提问里的 `E1` 可能指向完全不同的资料。

模型实际看到的内容可以更简单：

```text
只依据以下资料回答；资料不足时明确说明。结论请标注证据编号。
[E1] 员工福利制度 / 第 3 页 / v2：公司为工作日加班的员工提供每餐 30 元午餐补贴。
问题：午餐补贴是多少？
```

服务端则保留 `E1 → hr-v2-c003 → 原文位置与版本` 的映射，用于校验引用、展示来源。**出处由系统提供并绑定，不是让模型自己编文档名或链接。**

`hit` 与 `evidence` 最重要的区别是：**找到了，不等于给模型看了。** 正确资料可能已进入候选，却在阈值过滤、重排截断或上下文裁剪时被丢掉。一个证据也可能由多个相邻块合并而来，这时需要保留全部来源映射。

### 3.6 第四步：`answer`——不只保存答案文字

模型根据证据生成回答，服务端校验引用后，把文字、出处映射和排查标识一起组织成结果：

```json
{
  "text": "工作日加班的员工，午餐补贴为每餐 30 元。[E1]",
  "citations": [
    { "evidence_id": "E1", "chunk_id": "hr-v2-c003" }
  ],
  "refusal_reason": null,
  "run_id": "run-demo-001"
}
```

- **`text`：用户读到的内容。** 不只要保留“30 元”，也要保留原文的适用条件“工作日加班”。
- **`citations`：答案引用了哪些证据。** 前端可据此定位来源；服务端要检查编号是否属于本轮证据。编号合法也不等于结论正确，还需要检查证据是否真正支持结论。
- **`refusal_reason`：为什么不能回答。** 本例能够回答，因此为空；没有可用证据时可以记录 `insufficient_evidence`，并给用户明确的不足说明。检索到了资料但资料不能回答时，也应拒答或请求澄清。
- **`run_id`：这次问答的排查编号。** 由系统生成，用于关联本次查询、候选列表、实际证据、模型与索引版本等受控日志，不是让模型随意生成一个编号。

### 3.7 为什么要分成四个对象，而不是只留答案

它们不是把同一句话改四次名字，而是分别记录**资料本身、检索选择、上下文选择、最终表达**。前一步到后一步可以是一对多或多对一，不是四张必须逐条一一对应的数据表。

| 你观察到的现象 | 说明问题可能在哪一层 | 优先检查 |
| --- | --- | --- |
| 知识库里根本没有“30 元”这段资料 | 摄取层，或原文就没有 | 文档是否入库、解析是否漏字、切块是否拆散条件 |
| 有对应 `chunk`，但本次 `hit` 没有它 | 检索层 | 查询、授权范围、索引版本、召回数量与检索方式 |
| `hit` 找到了它，但 `evidence` 没有它 | 筛选与上下文组装层 | 阈值、重排、去重、版本筛选、长度预算 |
| `evidence` 有“30 元”，回答却说“50 元” | 生成层 | 实际 Prompt、模型输出、答案与证据一致性 |
| 回答金额正确，却漏了“工作日加班”条件 | 证据完整性或生成层 | 证据是否保留条件，模型是否扩大了适用范围 |
| 答案正确，点引用却跳到另一份文档 | 引用绑定层 | 本轮证据编号、块 ID、原文地址与版本映射 |

所以，调试时沿着 **`chunk → hit → evidence → answer`** 逐层追：**先确认资料进来了，再确认找到了，再确认交给模型了，最后确认模型用对了。** 不要一看到答案错误，就只修改提示词。

## 5、示例代码

[`examples/rag_demo.py`](https://github.com/tangjie-93/blog/blob/dev/docs/articles/rag/examples/rag_demo.py) 是本专题的基线：

- 只用 `Python` 标准库，通过 `HTTP` 调 OpenAI 兼容接口：硅基流动做嵌入、`OpenAI` GPT 做对话；

## 6、事实与版本约定

- 文章日期为 `2026-11-14`。涉及模型、价格、`stars`、许可证的信息会标注“快照”，使用前必须重新核对官方页面。

- 开源项目的许可证以仓库 `LICENSE` 为准。`Dify`、`FastGPT`、`WeKnora` 在 `GitHub API` 中显示为 `NOASSERTION`，属于自定义/修改条款，不能简单写成 `MIT` 或 `Apache-2.0`。
- 论文数字（如 `Contextual Retrieval` 的失败率下降）只在原实验设置下成立，不能直接当成本项目的预期收益。

## 7、一句话总结

`RAG` 不是“把文档塞给模型”，而是**建一套可追溯的证据供应链**：文档进得来、切得好、找得到、排得准、用得对、说得清、错得了可查。
