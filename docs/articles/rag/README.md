# `RAG` 团队培训手册

面向能读 `Python`、`HTTP` 和数据库文档的工程师。目标是能解释一次回答为什么正确或失败，并搭出带证据、可评测、可运维的知识库问答系统。

```text
01 原理 → 02 数据摄取 → 03 检索重排 → 04 生成引用
                      ↓
                 05 最小实战
                      ↓
06 评估 → 07 生产化 → 08 高级模式 → 09 培训计划
```

## 1、给初学者的总览

如果你从 `AI` 总路线进入，请先读 [05 `RAG` 与知识库总览](../ai/05-RAG与知识库.md)。它只解释概念和学习顺序；本专题的 01–08 章分别承载每一步的实现细节、知识点、失败案例和验收任务。

## 2、统一的数据契约

各章使用同一组中间对象，调试时沿着 `chunk → hit → evidence → answer` 追踪，而不是只看最终文本：

| 对象 | 必需字段 | 由谁产生 | 下一阶段检查什么 |
| --- | --- | --- | --- |
| `chunk` | `chunk_id`、正文、标题路径、页码、版本、`ACL`、内容哈希 | 数据摄取 | 是否可回到原文、是否可过滤 |
| `hit` | `chunk_id`、检索通道、分数、排名、过滤原因 | 召回/重排 | 正确证据是否进入 `top-k` |
| `evidence` | `chunk_id`、引用文本、版本、来源位置 | 上下文组织 | 每个事实是否有实际来源 |
| `answer` | 回答、引用、拒答原因、`run_id` | 生成层 | 是否只基于证据、是否可审计 |

当答案错误时，先问“正确的 `chunk` 是否进入 `hit`”，再问“模型是否正确使用 `evidence`”。这能把数据、检索和生成问题分开。

## 1、提交标准

每个小组提交一张链路图、一组 20 条带答案的问题、一份失败案例和一份可回滚的索引变更记录。培训中优先问“证据在哪里、版本是什么、用户是否有权限”。
