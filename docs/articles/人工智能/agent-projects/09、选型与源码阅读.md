## 3. 用五个问题读懂一个仓库

不要从目录第一行一路读到最后。先运行或手推一个最小任务，然后沿调用链找这些答案：

1. **输入是什么？** 是一句目标、结构化任务，还是已有工作流？数据在哪里校验？
2. **谁决定下一步？** 是模型选择工具、代码决定分支，还是二者混合？
3. **状态放在哪里？** 消息历史、当前步骤和中间产物是否分开？进程结束后能恢复什么？
4. **工具失败怎么办？** 超时、参数错误、权限不足、重复执行分别走哪条路径？
5. **谁判断完成？** 是模型说“完成”，还是代码或人检查了实际结果？

读完后写一段自己的说明：

```text
任务：读取某个仓库，整理项目定位与来源。
入口：接收仓库地址。
状态：保存待处理地址、采集结果和错误记录。
工具：读取 GitHub 元数据与项目说明。
退出：字段齐全或达到重试上限。
验收：链接有效，星数有采样日期，摘要不超出来源。
```

这只是阅读记录的示例，不宣称任一上榜项目恰好采用这套实现。

## 4. 最适合本站的第一个练习

建议题目：**把一个 `GitHub` 仓库整理成可以核对的项目卡片**。

第一版输入一个仓库地址，输出名称、定位、星数、采样时间、归档状态和来源。名称、数字、日期使用接口原值；模型只辅助分类和中文摘要。若仓库已经转移，保存规范地址，避免重复收录。

完成标准：

- 正常仓库能得到结构完整的卡片。
- 不存在或无权访问的仓库能解释失败，不编造字段。
- 遇到限流保留上次成功数据，不用空结果覆盖旧清单。
- 摘要中的每一项功能都能回到项目说明核对。
- 对已归档仓库明确标注；不以“未归档”代替“维护活跃”。

跑通后才扩展为“多个仓库去重 → 分类 → 人工确认 → 生成文章”。当流程完全可以用确定性代码完成时，就保持普通程序；遇到不规则说明的归纳才引入模型。这个练习可以验证你是否需要 `Agent`，而不是为使用框架而增加框架。

## 5. 用同一份记录比较两个候选

| 比较项 | 记录什么 |
| --- | --- |
| 任务成功 | 预先写好的验收条件是否通过 |
| 可解释性 | 能否看到每次工具调用、结果与失败原因 |
| 改造成本 | 接现有 `Node.js` 服务需要改哪些部分 |
| 运行成本 | 记录实际调用次数、耗时和模型费用，不引用宣传倍数 |
| 故障恢复 | 中断后是否重做全部任务，写操作会不会重复 |
| 维护与授权 | 阅读当前发布说明、关键问题讨论与实际许可证文本 |
| 替换难度 | 数据、提示、工具定义是否和框架实现强绑定 |

先选能完成当前任务且最容易解释的方案。只有出现明确瓶颈，再增加持久化、并发、多 `Agent` 或记忆系统。
