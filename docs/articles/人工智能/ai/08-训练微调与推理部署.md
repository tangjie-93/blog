# 08. 训练微调与推理部署

> 学习目标：分清预训练、SFT、偏好优化、LoRA、量化各自在改什么；能手算权重与 KV cache，并用明确的延迟、吞吐定义设计部署实验。
> 贯穿案例：团队知识助手已经能检索制度，但引用格式不稳定；访问高峰时长文档问答拖慢短问答。该先补知识、训练行为，还是调整服务调度？

## 1. 先定位缺口，再选择改变系统的方式

知识、行为和系统容量是三类问题。制度昨天更新而模型还说旧金额，优先修复检索和版本；已有正确证据却总漏掉引用格式，才值得考虑监督微调；排队太久则不是多训练几轮能解决的。

图中的链路不是“先微调才算上线”。每一阶段都应有退出条件：数据不可信不进入训练，压缩损伤关键任务不进入发布，平均性能提升却突破尾延迟预算也不通过。

| 方法 | 主要改变 | 团队助手适用情形 | 不能代替 |
| --- | --- | --- | --- |
| 提示词与输出 schema | 本次调用的任务约束 | 明确引用字段与拒答条件 | 服务端校验与权限 |
| RAG | 推理时可见的外部证据 | 频繁更新的制度、带出处回答 | 稳定行为训练 |
| 继续预训练 | 模型的领域语言分布 | 大量领域术语与文体适应 | 最新事实与可追溯引用 |
| SFT | 指令到目标回复的条件分布 | 格式、工具调用、领域工作流 | 对全部错误的保证 |
| 偏好优化 | 候选回答之间的相对偏好 | 在有用、简洁、谨慎之间校准 | 客观事实与权限规则 |
| LoRA | 参数更新的表示方式 | 减少任务适配的可训练参数 | 训练数据与目标设计 |
| 量化 | 数值表示与计算路径 | 降低权重或缓存占用 | 必然的提速或无损质量 |

## 2. 训练目标：预训练、SFT 与偏好优化

### 2.1 预训练：学习分布，不是建立事实数据库

以因果语言模型为例，常见目标是根据前面的 token 预测下一个 token，最小化负对数似然。预训练使用大规模语料；继续预训练在已有权重上使用领域语料，目标可以仍是语言建模，但语料比例、学习率和训练时长改变了风险。

如果只用企业手册继续训练，可能学会内部术语，也可能削弱通用能力或记住敏感文本。应先检查授权、去重、个人信息、文档版本以及通用回归集，而不是把所有网盘文件直接拼起来。

### 2.2 SFT：教模型“遇到这种输入怎样回应”

监督微调使用指令/上下文与目标回复。常见做法只对助手回复部分计算损失，让模型学习结构化输出、引用方式、适当拒答与工具调用；这与单纯阅读原始制度文本不同。

案例样本可以是：“已授权的第 3 页证据 + 用户问题 → 带 source_id 的答案”。训练中也要包含缺证据时的拒答和冲突版本处理；如果所有样本都强行给答案，模型会学到“无论证据多少都要答”。

高风险点是模板泄漏：同一制度的相近段落或改写问题同时出现在训练和测试中，会夸大泛化。按文档族、版本或时间分组划分，比随机打散每一行更可靠。

### 2.3 偏好优化：学习哪个回答更值得选

偏好数据常包含同一输入下的优选回答与较差回答。PPO 式 RLHF 通常先训练奖励模型，再用带约束的强化学习优化策略；DPO 则可直接利用成对偏好，通过相对参考模型的概率比构造目标，常见形式不需要独立奖励模型与在线 rollout。

DPO 不是“把好答案再做一次 SFT”，也不表示完全没有参考约束；参考模型及优化强度会影响偏移程度。若标注者只偏爱长答案，模型可能变得冗长，而非更正确。

对知识助手，先写清偏好准则：“证据正确优先于流畅，权限边界优先于完成任务，不能用无依据的细节换高分”。偏好优化之后仍需独立做事实与安全回归。

## 3. LoRA：改变更新方式，不是另一种知识来源

把一个线性层权重记为 `W ∈ R^(d_out×d_in)`。LoRA 冻结原权重，学习低秩更新：

```text
W' = W + s·BA
A: r×d_in，B: d_out×r，s 常与 alpha/r 有关
可训练参数 = r·(d_in+d_out)，而非 d_in·d_out
```

假设 `d_in=d_out=4096，r=8`，原层有 `16,777,216` 个参数，两个低秩矩阵共 `65,536` 个，只是原层的约 `0.39%`。这只是一层的教学计算，不代表整个模型显存会降到 0.39%。

基础权重、前向激活、反向计算、优化器状态仍要占用资源；把 LoRA 应用在哪些层、序列长度、batch、梯度检查点都会影响训练内存。rank 越大表达能力可能越强，但也增加训练开销，效果并非必然单调提升。

LoRA 可用于 SFT，也可用于偏好优化；前者回答“优化什么目标”，后者回答“哪些参数怎样更新”。适用实现中可把增量合并到基础权重，减少推理分支，但多适配器动态切换、量化与合并流程需要分别验证。

| 参数高效适配选择 | 主要取舍 |
| --- | --- |
| 小 rank、少量目标层 | 更省训练参数，但可能无法覆盖复杂行为变化 |
| 更高 rank、更多目标层 | 表达能力与适配成本同时提高 |
| 独立加载适配器 | 方便多租户版本切换，需隔离适配器与缓存 |
| 合并权重发布 | 部署路径更单一，需单独管理合并产物和回滚 |

## 4. 量化：减少位宽，不能只看“能装下”

量化通过缩放、舍入等过程，把权重或激活映射为较低精度表示。PTQ 在训练后进行，可能用校准数据寻找范围；QAT 在训练中模拟量化误差。权重量化、激活量化和 KV cache 量化是不同开关。

某些低比特格式按组保存 scale、zero-point 和元数据，实际占用高于理想的“参数量×位宽”。如果推理内核不支持目标硬件、需要频繁反量化，省内存也不必然更快。

团队助手量化后要特别复核：中文专名、金额、长上下文引用、JSON 合法性、工具参数和拒答边界。校准集需要代表真实长短输入与语言分布，不能拿最终盲测集反复调校准策略。

## 5. 内存预算：先写假设，再算容量

### 5.1 权重只是底座

假设一个恰有 `7×10⁹` 参数的稠密模型，推理权重全为 BF16，每参数 2 字节，则权重为 `14×10⁹ B ≈ 13.04 GiB`；这里 `1 GiB=2³⁰ B`。理想 4-bit 权重为 `3.5×10⁹ B ≈ 3.26 GiB`，**尚未包含**量化元数据、未量化层、运行时与缓存。

训练内存不能套用这个推理值。作为另一个**简化假设**，若全参训练每参数保存 BF16 权重 2 B、BF16 梯度 2 B、FP32 主权重 4 B、FP32 Adam 两个状态 8 B，共 16 B，则 7B 参数约占 112 GB，即 104.31 GiB，仍未计激活与通信缓冲。

实际混合精度方案、优化器、分片、卸载与检查点会改变上述组成；这个估算只用于理解量级，不能当作设备采购承诺。

### 5.2 KV cache 随上下文与并发增长

自回归解码为每层保存历史 token 的 key 和 value，避免重复计算旧 token 的 K/V。对简化的全缓存注意力模型：

```text
KV 字节数 ≈ 2 × 层数 L × KV 头数 Hkv × 头维度 D × 缓存 token 总数 T × 每元素字节 b
```

假设 `L=32，Hkv=8，D=128，b=2`，每 token 的 KV 为 `131,072 B = 128 KiB`。单请求 4096 个已缓存 token 约 `0.5 GiB`；8 条这样的请求约 `4 GiB`。这里 T 包括已缓存的提示与输出 token，不是仅输出长度。

该假设采用 GQA 的 8 个 KV 头；若改成 32 个 KV 头，其余不变，KV 占用会变成 4 倍。滑动窗口、共享前缀、缓存压缩、量化和分片都会改变实际占用。

| 简化推理组成 | 估算 |
| --- | --- |
| 7B BF16 权重 | 13.04 GiB |
| 8×4096 token 的上述 KV | 4.00 GiB |
| 仅以上小计 | 17.04 GiB，不代表峰值显存 |
| 尚未计算 | 激活、临时工作区、图捕获、碎片、框架保留与安全余量 |

PagedAttention 把逻辑连续的 KV 映射到可不连续的物理块，重点解决分配与共享效率；它不会让注意力不再需要 KV，也不会保证任意长上下文都能装下。

## 6. 请求时间线：prefill 与 decode 为什么要分开看

**Prefill** 处理提示 token 并建立缓存，可在提示内部并行计算；长文档会带来更大的计算与内存压力。**Decode** 依赖前一个输出逐步生成，单步常受权重读取、KV 访问和并发调度影响，具体瓶颈取决于模型与硬件。

```text
到达 → 排队 → prefill → 首 token → decode → 最后 token
       └────── TTFT ────────┘
到达 ───────────────────────→ 端到端延迟
```

客户端 TTFT 是请求发出到首 token 到达，通常含网络；服务端可另报排队与计算时间。ITL 是相邻输出 token 到达间隔；TPOT 常按首末 token 时间差除以后续 token 数计算。必须注明测量端点与分母。

假设首 token 在 0.6 秒到达，100 个输出 token 的后续平均间隔为 0.02 秒，则末 token 大约在 `0.6 + 99×0.02 = 2.58` 秒到达，不是 100×0.02。输出长度不同，不应只比较总延迟。

### 6.1 吞吐与用户等待之间的张力

连续批处理允许请求在解码过程中加入或退出，比等整批结束更灵活。但不断增加并发会占用更多 KV，超过容量后可能排队、抢占或重算，p95 不一定随吞吐改善。

| 手段 | 可能改善 | 必须同时观察 |
| --- | --- | --- |
| 增大批次或并发 | 总输出 token/s、设备利用率 | TTFT、TPOT、排队与显存 |
| 分块 prefill | 缓和长提示对短请求的阻塞 | 长提示完成时间与调度开销 |
| 前缀缓存 | 重复前缀的 prefill 成本 | 命中率、版本与租户隔离，不是答案缓存 |
| 张量并行 | 容纳更大模型、分摊计算 | 跨卡通信、拓扑和小批延迟 |
| 推测解码 | 合适草稿模型下减少目标模型调用 | 接受率、额外开销与输出分布实现保证 |

对知识助手可以区分交互短问答与离线长报告队列，限制最大输入/输出，设置超时与取消传播。不能为了展示高吞吐，把交互请求无限堆进队列。

## 7. 标准库实验：从原始时间戳算指标

以下是**合成日志**，用来验证统计口径，不是服务压测结果。保存为 `serving_metrics.py` 并执行 `python3 serving_metrics.py`；所有时间单位为秒、同一时钟，首末 token 都在客户端记录。

```python
import math
import statistics

rows = [
    # 到达、首 token、末 token、输出 token 数
    (0.0, 0.20, 1.18, 50),
    (0.1, 0.35, 1.33, 50),
    (0.2, 0.50, 1.48, 50),
    (0.3, 0.70, 1.68, 50),
    (0.4, 1.40, 2.38, 50),
]

def percentile_nearest_rank(values, p):
    values = sorted(values)
    return values[math.ceil(p * len(values)) - 1]

ttft = [first - arrival for arrival, first, last, n in rows]
e2e = [last - arrival for arrival, first, last, n in rows]
tpot = [(last - first) / (n - 1) for arrival, first, last, n in rows]
window = max(r[2] for r in rows) - min(r[0] for r in rows)
tokens = sum(r[3] for r in rows)
print("TTFT p50/p95:", round(statistics.median(ttft), 3),
      round(percentile_nearest_rank(ttft, 0.95), 3))
print("E2E p95:", round(percentile_nearest_rank(e2e, 0.95), 3))
print("平均 TPOT:", round(statistics.mean(tpot), 3))
print("窗口输出 token/s:", round(tokens / window, 2))
assert math.isclose(statistics.median(ttft), 0.30)
assert math.isclose(max(ttft), 1.00)
assert all(math.isclose(x, 0.02) for x in tpot)
```

预期：TTFT p50 为 `0.3`、p95 为 `1.0`，E2E p95 为 `1.98`，平均 TPOT 为 `0.02`，窗口输出吞吐约 `105.04 token/s`。这里只有 5 条，最近秩 p95 等于最大值，不能据此证明真实尾延迟稳定。

窗口吞吐用“全部输出 token/整个观测窗口”，不能把每请求 token/s 简单相加。真实实验还需单列成功请求吞吐、错误与超时、输入 token/s；失败请求不能悄悄从可用性分母消失。

### 7.1 可复现的真实 A/B 协议

1. 固定权重/适配器哈希、服务版本、硬件、驱动、精度、提示模板、采样参数与请求集；保存输入/输出长度分布。
2. 准备脱敏的短、中、长上下文分层样本；质量盲测集不参与调参，明确冷缓存与热缓存分别测试。
3. 预热后分别以固定到达速率逐级加压；记录并发、排队、取消、错误、显存和客户端原始时间戳，不能只做闭环“完成一个再发一个”。
4. 每次只变一个因素，如 BF16→量化；重复至少 3 轮，报告测试窗口和样本量，比较每层质量及 p50/p95，而非只给总体均值。
5. 先设 SLO 再找满足 SLO 的最大负载；达到超时、错误或质量门禁时停止加压，保留旧版回滚路径。

这是一份实验协议，不包含虚构硬件跑分。真实硬件不可用时，先运行合成日志实验，完成统计代码验证，不要把它包装成模型性能测试。

## 8. 失败诊断：找到瓶颈再加资源

| 现象 | 优先判断 | 可尝试的取舍 |
| --- | --- | --- |
| 训练损失降、独立测试变差 | 重复泄漏、过拟合、训练/业务分布差异 | 改数据和早停，而非继续加 epoch |
| LoRA 显存仍不足 | 长序列激活、基础权重、优化器 | 缩序列/微批、检查点、分片；参数少不等于激活少 |
| 权重能装但一并发就 OOM | KV 预算和峰值工作区 | 限上下文与并发，测 KV 精度和缓存策略 |
| TTFT 高、TPOT 正常 | 排队、长 prefill、缓存未命中 | 调度隔离、分块 prefill、减少无关上下文 |
| TPOT 高、TTFT 尚可 | decode 带宽、KV 访问、通信 | 检查批次、内核与并行拓扑，避免盲目加卡 |
| 量化省内存但更慢 | 内核不匹配、反量化开销 | 换受支持格式或回滚，而非接受宣传结论 |
| 格式通过但金额错误 | 训练只优化外形、事实未验证 | 回到证据与业务校验，不能只加 JSON 样本 |

发布包应能追溯数据版本、许可证、训练配置、权重/适配器、量化配置与服务镜像。灰度前准备限流、超时、熔断、健康检查、成本上限和一键回滚；指标与安全门禁见下一篇。

## 9. 分层练习与自测答案

1. **入门**：制度昨天修改，回答仍旧；已有正确证据却不输出引用。这两类问题应优先采用同一种办法吗？
2. **机制**：SFT 与 LoRA 为什么不是互斥选项？量化和 LoRA 又分别解决什么？
3. **计算**：上述 KV 配置下，16 条各缓存 8192 token 的请求占多少 GiB？单请求上下文翻倍为何会压缩可接纳并发？
4. **实验**：合成日志删掉最慢请求后 p95 改善，能说明系统改善吗？应该同步报告什么？
5. **挑战**：量化版窗口吞吐提升但长文档引用准确率下降，怎样决定是否发布？

**答案要点**：① 前者查 RAG 更新和版本，后者先改提示/schema，稳定行为缺口再考虑 SFT。② SFT 是目标，LoRA 是低秩参数更新方式；量化主要改变数值表示与运行路径。③ `16×8192×128 KiB = 16 GiB`，固定显存预算下 KV 随 token 总数增长。④ 不成立，可能是幸存者偏差；保留到达样本，报告失败、超时与取消率，并说明延迟分布是否仅对成功请求计算。⑤ 预先设关键质量门禁，定位分层退化，修复或回滚；不能用平均吞吐抵销高风险业务错误。
