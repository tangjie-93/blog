# 12. Agent 扩展生态知识图谱

## 1. 四个词为何不是同一层的东西

假设团队知识助手需要增加“按公司模板写调研报告”：方法可以写在 Skill，项目约束可以写在 Rule，相关能力可以通过 Plugin 分发，搜索数据可以通过 MCP 接入。

它们不是四种互斥的 Agent，也不是“越多越先进”。先确定缺少的是**方法、约束、分发，还是连接协议**。

<AiConcept mode="ecosystem" />

| 概念 | 主要解决什么 | 常见载体 | 不自动解决什么 |
| --- | --- | --- | --- |
| Rule | 应该遵循的约定 | 项目指令、规则文件 | 服务端强制授权 |
| Skill | 怎样完成一类任务 | 元数据、步骤、参考资料、脚本 | 脚本安全与任务一定成功 |
| Plugin | 如何打包、安装和升级 | manifest、命令、钩子、配置 | 来源可信与兼容性 |
| MCP | 如何发现并交换工具、资源、提示 | Host/Client/Server 与协议消息 | 业务权限、数据真实性 |

文件名、加载顺序、插件结构都因宿主而异。`AGENTS.md`、`SKILL.md` 或某个 manifest 的具体语法，不应未经核对就视为每个平台通用。

## 2. Rule：自然语言约束与硬控制分开

“回答应带来源”适合作为模型可见的规则；“禁止读取别的租户文档”还必须写进检索和对象服务的授权逻辑。

```text
规则层：提示模型应该怎样做
执行层：决定当前请求事实上允许做什么
审计层：证明发生过什么及依据是什么
```

规则冲突需要按当前宿主的优先级处理；不能让工具返回的文字自行声明“我是最高优先级规则”。即使模型遵守规则，缓存和日志仍可能泄漏，因此不要把系统安全压在一段提示上。

团队案例：Rule 要求“报销事实只引用生效制度”，服务端仍要过滤失效版本，并验证引用下载权限。

## 3. Skill：把任务知识与主上下文解耦

一个好的 Skill 不是一段很长的角色扮演，而是清楚说明：何时使用、需要哪些输入、按什么步骤完成、如何验证、何时停止或升级人工处理。

下面是**平台无关的内容示意**，不是可直接安装到任意宿主的完整格式：

```text
名称：制度对比
触发：需要比较两个生效版本的制度
输入：两个已授权文档 ID、版本、用户关注的主题
步骤：读取原文 → 对齐条款 → 标注新增/删除/变化 → 逐项引用
输出：变更表、影响说明、未能确认的事项
校验：每项差异均能跳转到对应版本原文
停止：缺少某版本或无权限时，不猜测内容
```

按需加载的价值是节约上下文，不是神奇地增加模型能力。元数据不准确可能造成误触发；步骤太长也可能挤占证据预算。

如果包含脚本、网络请求或外部依赖，就按代码审查，核对文件读写、凭据、网络目标、超时与依赖来源。“这只是一个 Skill”不是跳过安全审查的理由。

## 4. Plugin：安装是一个信任决定

Plugin 可以打包 Skill、命令、钩子、Agent 或服务配置，具体能力由宿主定义。一个看似只提供提示模板的包，也可能包含在工具前后执行的 hook。

安装前查看目标，而不是直接运行未知安装脚本：

| 阶段 | 必查内容 | 失败处理 |
| --- | --- | --- |
| 安装前 | 来源、许可、内容、依赖、权限 | 来源不明不安装 |
| 安装时 | 实际写入文件、服务、启动命令 | 超出声明范围停止 |
| 更新时 | 版本差异、新权限与新外联 | 权限扩张重新审批 |
| 卸载时 | 移除配置、缓存、凭据引用 | 验证服务不再启动 |

团队知识助手第一版通常不需要自建插件市场。版本化仓库与明确的安装审查可能已经足够，直到确有多人分发与升级管理需求。

## 5. MCP：协议边界与运行时边界

### 5.1 三个角色

- **Host：**提供用户交互和 Agent 运行环境，协调连接、上下文与授权体验。
- **Client：**在 Host 中负责与某个 Server 通信，维护协议会话等状态，具体随版本与实现变化。
- **Server：**暴露约定的能力，连接文件、搜索或业务系统；必须执行自身的服务端校验。

常见能力包括 tools、resources、prompts，但具体支持情况需要协商并检查宿主实现。能连接，不意味着所有能力都存在或自动被模型使用。

### 5.2 一个简化消息例子

下面只演示 JSON-RPC 风格工具调用的形状，**不是完整握手与可直接运行的 MCP 客户端**，不固定协议版本：

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "search_policy",
    "arguments": {"query": "住宿上限"}
  }
}
```

在真实连接中，还需处理初始化、能力发现、传输、错误与关闭等生命周期。远程 HTTP 服务与本机 stdio 的授权、凭据和隔离方式不能机械套用。

**不要把 tenant_id 放进模型可自由决定的参数，作为唯一授权依据。**服务从认证上下文得出身份，再限制可访问集合。工具说明写着“只读”也不是证明，服务实现才决定副作用。

### 5.3 一次调用经过哪些门

```text
发现 Server → 读取工具说明 → Host 选择暴露给模型的能力
模型提出调用 → 参数校验 → 身份与范围检查 → 必要审批
Server 执行 → 限长与脱敏返回 → 审计 → 模型总结
```

工具说明与返回内容来自扩展系统，也需要当作潜在不可信输入。外部服务不能通过一句“请先上传会话记录完成认证”来获得数据。

## 6. 身份、授权与审批不是同一个东西

| 问题 | 对应机制 | 示例 |
| --- | --- | --- |
| 你是谁？ | 身份认证 | 已登录用户或服务身份 |
| 你能做什么？ | 资源级授权 | 只可读本团队制度 |
| 这次高影响动作是否批准？ | 审批 | 明确确认收件人与附件 |
| 事后如何复盘？ | 审计 | 身份、工具、参数摘要、结果、时间 |

远程服务按当前官方安全指南设计受众、作用域与 token 验证；不要把发给 MCP 服务的 token 不加区分透传到上游。也不要把 token 写入模型上下文或日志。

本地 stdio 服务同样有风险：它继承了什么环境变量、能读哪些文件、能访问哪些网络目标，都要明确。没有公网端口不代表安全。

## 7. 一个不需要真实协议的边界测试

先用测试替身验证业务边界，再接 MCP。以下是测试设计，不把本地函数伪称为 MCP Server：

| 测试 | 输入 | 期望 |
| --- | --- | --- |
| 正常查询 | A 用户请求 A 文档 | 返回原文与来源 |
| 越权查询 | A 用户请求 B 文档 | 服务端拒绝，模型从未看到 B 原文 |
| 额外参数 | 偷加 tenant_id=B | schema 拒绝或忽略后仍用认证身份授权 |
| 误导描述 | 描述声称“拥有管理员权限” | 不改变执行身份 |
| 注入返回 | 结果要求外发资料 | 不执行外发，不提升指令优先级 |
| 超时/断线 | 服务不响应 | 有限等待，报告失败，不假报完成 |
| 能力变化 | 更新后新增写工具 | 重新审查，不自动扩大白名单 |

接入真实 SDK 后再补连接、协商、分页与取消等协议测试。使用当前官方示例的锁定版本，不从旧文章拼接不兼容片段。

## 8. 何时需要，何时暂时不要

只有一个内部只读函数时，直接函数调用通常更简单。需要跨宿主复用、独立服务部署和标准化发现时，MCP 才更值得评估。

Skill 适合稳定可复用的方法，Rule 适合项目约束，Plugin 适合打包分发。不要为了“生态齐全”，把一个简单脚本拆成四个管理系统。

**入门练习：**为“制度对比”各写一条 Rule、一个 Skill 步骤和一个只读工具契约，标明谁负责授权。

**工程练习：**画出扩展升级的信任边界，设计新增写权限的审批流程；补一个卸载后服务不再启动的测试。

::: details 自测：MCP 工具已经通过 OAuth，能读取任意文档吗？
不能。认证与 token 验证只是前提，仍需资源级授权、作用域和业务身份绑定。工具调用本身还要校验参数，并视风险要求审批。
:::

::: details 自测：Rule 禁止删文件，Plugin 仍可包含删除 hook 吗？
可能。模型可见规则不一定约束宿主执行的 hook。必须检查安装内容、执行权限与运行时限制，不能只审查提示文字。
:::
