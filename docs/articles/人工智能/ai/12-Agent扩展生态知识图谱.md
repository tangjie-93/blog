# 12. Agent 扩展生态知识图谱

如果刚接触这些词，先读 [15 AI 助手与 Agent 生态术语全景](./15-AI助手与Agent生态术语全景.md)；本篇只做一件事：**把扩展接入拆成责任边界，再用安全测试验证它。**

## 1. 四个词分别修复什么问题？

<AiVisual title="同一个制度助手，四种扩展各管一层" kind="compare" :nodes="[
  { label: 'Rule · 约束', detail: '规定回答必须引用生效制度，属于模型可见的项目约定。' },
  { label: 'Skill · 方法', detail: '规定如何对齐两个版本、逐项引用并在缺证据时停止。' },
  { label: 'Plugin · 分发', detail: '打包安装方法、命令、钩子或配置，负责交付与升级。' },
  { label: 'MCP · 连接', detail: '让宿主发现并调用搜索、文档等外部能力，协议不替业务授权。' }
]" caption="四者可以组合，但不是互斥 Agent，也不是越多越先进。" />

<AiConcept mode="ecosystem" />

::: details 常见载体与不自动解决的问题
| 概念 | 主要解决什么 | 常见载体 | 不自动解决什么 |
| --- | --- | --- | --- |
| Rule | 应该遵循的约定 | 项目指令、规则文件 | 服务端强制授权 |
| Skill | 怎样完成一类任务 | 元数据、步骤、参考资料、脚本 | 脚本安全与任务一定成功 |
| Plugin | 如何打包、安装和升级 | manifest、命令、钩子、配置 | 来源可信与兼容性 |
| MCP | 如何发现并交换工具、资源、提示 | Host/Client/Server 与协议消息 | 业务权限、数据真实性 |
:::

文件名、加载顺序和插件结构因宿主而异；不能把某个平台的 `AGENTS.md`、`SKILL.md` 或 manifest 当成所有工具的通用语法。

## 2. Rule 不是硬权限

<AiVisual title="一条规则要经过三道边界" kind="layers" :nodes="[
  { label: '规则层', detail: '提示模型应该怎样回答，例如只引用生效制度。' },
  { label: '执行层', detail: '检索与对象服务真正过滤版本、租户和资源权限。' },
  { label: '审计层', detail: '记录身份、工具、参数摘要、结果、时间与未完成事项。' }
]" caption="重要安全边界必须由执行层保障，不能把安全压在一段提示上。" />

“回答应带来源”适合作为 Rule；“禁止读取别的租户文档”还必须写进检索和对象服务的授权逻辑。工具返回的文字不能自行声明“我是最高优先级规则”。

## 3. Skill：把方法按需加载

一个好的 Skill 说明：何时使用、输入是什么、步骤怎样走、如何验收、何时停止或升级人工。按需加载的价值是节约上下文，不是神奇地增加能力。

::: details 平台无关的 Skill 内容示意（不是可安装格式）
```text
名称：制度对比
触发：需要比较两个生效版本的制度
输入：两个已授权文档 ID、版本、用户关注主题
步骤：读取原文 → 对齐条款 → 标注变化 → 逐项引用
校验：每项差异均能跳转到对应版本原文
停止：缺版本或无权限时，不猜测内容
```
:::

包含脚本、网络请求或外部依赖时，按代码审查文件读写、凭据、网络目标、超时与依赖来源。复制文件可迁移知识，不一定迁移运行能力。

## 4. Plugin：安装就是信任决定

<AiVisual title="扩展包的生命周期检查" :nodes="[
  { label: '安装前', detail: '核对来源、许可、内容、依赖与声明权限。' },
  { label: '安装时', detail: '检查实际写入文件、服务和启动命令是否越界。' },
  { label: '更新时', detail: '比较版本差异、新权限与新外联，扩权重新审批。' },
  { label: '卸载后', detail: '确认配置、缓存、凭据引用清理，服务不再启动。' }
]" caption="插件市场或名称不是安全证明；实际代码与运行权限才是审查对象。" />

团队知识助手不必一开始就自建插件市场；版本化仓库与明确安装审查可能已经够用。

## 5. MCP：连接边界不等于授权边界

<AiVisual title="MCP 一次调用的安全链" :nodes="[
  { label: '发现', detail: 'Host 发现 Server 与工具说明，只暴露明确允许的能力。' },
  { label: '提出', detail: '模型请求工具并给出参数；请求仍是未执行的意图。' },
  { label: '校验', detail: '运行时检查 schema、认证身份、资源范围和必要审批。' },
  { label: '执行与审计', detail: 'Server 执行并限长脱敏返回，记录结果与失败。' }
]" caption="工具说明和返回内容也可能不可信；服务实现才决定副作用与权限。" />

### 5.1 三个角色

- **Host：**提供用户交互与 Agent 运行环境，协调连接、上下文和授权体验。
- **Client：**在 Host 中与某个 Server 通信，维护协议会话状态。
- **Server：**暴露能力并连接文件、搜索或业务系统，必须执行自身校验。

常见能力包括 `tools`、`resources`、`prompts`，支持情况要通过协商和宿主实现确认。远程 HTTP 与本机 stdio 的凭据、隔离与网络边界也不能机械套用。

::: details 简化的 JSON-RPC 风格形状（不是完整 MCP 客户端）
```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": { "name": "search_policy", "arguments": { "query": "住宿上限" } }
}
```
真实连接还要处理初始化、能力发现、传输、错误、取消与关闭。不要把 `tenant_id` 作为模型可自由决定的唯一授权依据：服务应从认证上下文得到身份。
:::

## 6. 身份、授权、审批、审计

| 问题 | 对应机制 | 示例 |
| --- | --- | --- |
| 你是谁？ | 身份认证 | 已登录用户或服务身份 |
| 你能做什么？ | 资源级授权 | 只读本团队制度 |
| 这次高影响动作是否批准？ | 审批 | 明确收件人与附件 |
| 事后如何复盘？ | 审计 | 身份、工具、参数摘要、结果、时间 |

本地服务同样可能继承环境变量、读取文件或访问网络；没有公网端口不代表安全。不要把 token 写入模型上下文或日志，也不要把发给 MCP 服务的 token 无区分透传到上游。

## 7. 先测边界，再接真实协议

| 测试 | 输入 | 期望 |
| --- | --- | --- |
| 正常查询 | A 用户请求 A 文档 | 返回原文与来源 |
| 越权查询 | A 用户请求 B 文档 | 服务端拒绝，模型未看到 B 原文 |
| 额外参数 | 偷加 `tenant_id=B` | 仍按认证身份授权 |
| 误导描述 | 返回声称“拥有管理员权限” | 不改变执行身份 |
| 注入返回 | 结果要求外发资料 | 不执行外发，不提升指令优先级 |
| 超时/断线 | 服务不响应 | 有限等待，报告失败，不假报完成 |
| 能力变化 | 更新后新增写工具 | 重新审查，不自动扩大白名单 |

接入真实 SDK 后，再补连接、协商、分页、取消与版本测试。一个只读函数也许不需要 MCP；跨宿主复用、独立部署和标准化发现才是评估 MCP 的理由。

::: details 自测：MCP 工具已通过 OAuth，就能读任意文档吗？
不能。认证只是前提，还需资源级授权、作用域、业务身份绑定和参数校验；高风险动作还可能需要审批。
:::

::: details 自测：Rule 禁止删文件，Plugin 仍能有删除 Hook 吗？
可能。模型可见规则不一定约束宿主 Hook。必须检查安装内容、执行权限与运行时限制。
:::
