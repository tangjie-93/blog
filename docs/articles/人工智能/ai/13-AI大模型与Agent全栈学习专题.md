# 13. AI 全栈能力矩阵与进阶项目

## 1. 这页不是另一份入门路线

入门顺序见[专题导读](./)，阶段任务见 [11 实战里程碑](./11-学习路线与实战任务.md)。本页面向已经跑过最小应用的读者，解决两件事：**定位能力短板；选择值得深入的实现问题。**

全栈不是同时精通模型科学、GPU 内核和产品治理。它首先意味着知道各层的契约，能发现问题属于哪一层，知道何时需要其他专业角色参与。

## 2. 能力矩阵：从“听过”到“能验证”

给自己打级别时附证据，而不是凭熟悉程度：

- **L0：**只能解释词语。
- **L1：**能运行既有例子并追踪输入输出。
- **L2：**能写测试、制造失败并说明机制。
- **L3：**能在约束下做取舍，提供对照结果与回滚方案。

| 层 | L1 证据 | L2 证据 | L3 证据 |
| --- | --- | --- | --- |
| 数学与训练 | 跑通训练循环 | 手算梯度、有限差分验证 | 识别切分泄漏与代理目标偏差 |
| Transformer | 打印张量 shape | mask 不变量与数值对照 | 区分算术、带宽与激活内存瓶颈 |
| 生成与协议 | 调用模型输出 JSON | top-p 边界、截断与校验测试 | 任务路由与成本/质量回归 |
| 数据与检索 | 构建索引 | 版本、ACL、召回诊断 | 更新删除、重建切换与漂移分析 |
| Agent 运行时 | 跑工具循环 | 授权、预算、失败恢复 | 副作用一致性与可审计恢复 |
| 扩展生态 | 连接外部工具 | 能力变化与权限回归 | 安装升级信任链与最小权限 |
| 服务与性能 | 暴露推理服务 | 分层负载与原始时间戳 | SLO 约束下容量、限流、降级 |
| 评估与治理 | 运行固定题集 | 分母、分桶、配对回归 | 风险门禁、事故与回滚演练 |

不要对每一行都追求 L3。应用负责人需要能够横向讨论这些边界；特定优化问题则需要在一两行深挖。

## 3. 进阶项目 A：可检查的微型语言模型

**前提：**能解释 01–03 的数学、attention 与采样。

**任务：**使用 PyTorch 构建小型 decoder，包含 tokenizer/词表、embedding、位置方案、因果注意力、MLP、残差、词表投影和错位标签。数据采用自有或许可明确的小文本，不追求大模型效果。

必须先通过以下不变量测试：

1. 改变未来 token，过去位置 logits 不变（评估模式，固定其他条件）。
2. padding 不参与损失；有效 token 计数正确。
3. 无缓存与有缓存生成的 logits 在数值容差内接近。
4. 保存并加载 checkpoint 后，固定输入输出可对照。
5. 只用小样本过拟合能说明训练链路工作，不能当泛化证明。

**实验：**一次只改位置方案、头数或上下文长度之一，记录验证损失、实际内存、计算时间与生成失败。

**设计评审问题：**参数变多但验证损失没改善，先查数据量、训练预算还是架构？如何区分？

源码入口：[nanoGPT](https://github.com/karpathy/nanoGPT)、[LLMs from scratch](https://github.com/rasbt/LLMs-from-scratch)。教学仓库不是无条件适合生产的服务框架。

## 4. 进阶项目 B：可追溯的知识库更新

**前提：**已完成 04–05 的单版本问答。

**任务：**让团队知识助手支持制度新增、替换、撤回，以及不同租户的权限变化；每个答案可回到当时使用的版本。

```text
原始对象版本 → 解析版本 → chunk 集合 → 索引快照
                                    ↓
请求授权上下文 → 可用索引版本 → 候选 → 回答与引用
```

必须回答的边界：

- 新索引构建失败时，旧索引是否继续服务？
- 切换成功后，旧答案缓存何时失效？
- 彻底删除一份文档，要处理哪些对象、向量、缓存、日志和备份？
- 历史回答有旧引用，是允许按历史权限查看，还是显示已撤销？
- ACL 修改与缓存不同步时，怎样避免先泄漏再补救？

**实验：**在构建、切换和删除的不同阶段注入失败，检查服务状态与审计记录。质量测试之外，单独测试删除与撤权的完成条件。

源码与深入教程见 [RAG 生产化](../rag/10-生产化.md)，不要用换向量库代替生命周期设计。

## 5. 进阶项目 C：可恢复的受限工作流

**前提：**已经有 06 的只读工具循环与服务端授权。

**任务：**先做低风险工作流：“查询资料 → 起草报告 → 用户确认后保存到指定测试目录”。外发邮件与真实业务写入暂不启用。

**状态至少包含：**任务 ID、阶段、证据版本、已完成步骤、待审批动作、预算、幂等键、工具结果引用、失败原因。

| 中断位置 | 需要证明什么 |
| --- | --- |
| 模型提出动作后、执行前 | 恢复时仍需校验当前权限 |
| 工具执行成功、结果尚未持久化 | 不盲目重做；先按幂等键查询实际结果 |
| 人工批准后隔了很久 | 资源与内容改变时旧审批不能无条件复用 |
| 达到预算后 | 停止，保留可理解的部分结果 |
| 工具返回与记录状态冲突 | 显式进入待核对状态，而不是假报成功 |

**工程难点：**“记录了日志”不等于具备一致的恢复语义。真正的写操作需要把幂等与业务事务放到工具服务中设计。

源码入口：[LangGraph](https://github.com/langchain-ai/langgraph)，对照普通状态机实现同一个任务，记录框架带来的真实收益和额外约束。

## 6. 进阶项目 D：有成本证据的多 Agent 对照

不是因为“研究员、审稿人、写作者”听起来合理就需要三个 Agent。只有子任务可独立完成，且交接契约明确，才值得实验。

先有单 Agent 基线，再构造可并行的两条资料线；每个子任务输出固定字段：`结论、证据 ID、未解决问题、消耗与停止原因`。

对同一题集比较：

- 总任务成功与引用支持，而非各角色自评分。
- 端到端耗时与所有角色 token 总和。
- 证据交接丢失、重复工作、相互矛盾和合并失败。
- 一个角色超时后，最终结果如何注明缺口。

只有收益超过编排、校验与成本代价，才保留多 Agent。系统复杂度本身不是研究成果。

## 7. 进阶项目 E：受 SLO 约束的部署

用 08 的指标方法，不从“支持多少并发”这种孤立数字开始。固定模型、硬件、长度分布、精度与到达速率，逐步增加负载。

**报告最少包含：**请求数、测试时长、冷/热缓存、成功/错误/超时、TTFT 与端到端 p50/p95、输出吞吐、峰值显存与质量回归。

先问交互任务能否接受排队，再决定批次；先算 KV 再设上下文上限；先测量化对关键任务的影响，再庆祝省内存。

没有真实硬件时，用合成时间戳验证统计代码，并明确标为合成实验，不发布虚构跑分。

## 8. 一份真正有用的设计评审

提交项目时，先展示一个失败案例，而不是最好看的演示：

1. 用户意图和允许的系统行为是什么？
2. 哪些输入不可信，哪些身份与授权由程序保证？
3. 每一层输入输出与版本怎样记录？
4. 为什么选择这个组件，简单替代方案是什么？
5. 改动提升了哪类样本，退化了哪类样本？
6. 质量、延迟、成本与安全之间怎样权衡？
7. 哪些结果是手算、合成、真实测量，哪些尚未验证？
8. 怎样回滚，谁负责残余风险？

::: details 自测：能解释论文并复现小实验，就能负责生产系统吗？
不自动成立。生产还需要数据权限、服务稳定性、更新删除、监控、事故响应与组织治理。反过来，会部署成熟模型也不等于掌握训练原理；能力证据应分层陈述。
:::
