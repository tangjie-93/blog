# 13. AI 全栈能力矩阵与进阶项目

入门顺序见[专题导读](./)，阶段任务见 [11 实战里程碑](./11-学习路线与实战任务.md)。本页不再重复入门路线，而是帮助已经跑过最小应用的读者：**定位短板，选择一个值得深入并能拿出证据的实现问题。**

## 1. 全栈不是“每层都精通”

<AiVisual title="从一个问题定位到正确层次" :nodes="[
  { label: '现象', detail: '答案错、工具越权、延迟升高或更新后回归。' },
  { label: '契约', detail: '确认输入输出、版本、权限和验收指标属于哪一层。' },
  { label: '证据', detail: '用测试、日志、张量、检索结果或测量数据复现失败。' },
  { label: '取舍', detail: '选择修复、降级或回滚，并说明剩余风险。' }
]" caption="排查流程示意；不要因为模型输出异常就默认换模型。" />

全栈首先意味着能横向讨论模型、数据、运行时、服务和治理的边界，知道什么时候需要其他专业角色参与。能力等级要附证据：

- **L0**：只能解释词语。
- **L1**：能运行既有例子并追踪输入输出。
- **L2**：能写测试、制造失败并说明机制。
- **L3**：能在约束下做取舍，提供对照结果与回滚方案。

| 层 | L1 证据 | L2 证据 | L3 证据 |
| --- | --- | --- | --- |
| 数学与训练 | 跑通训练循环 | 手算梯度、有限差分 | 识别切分泄漏与代理目标偏差 |
| Transformer | 打印张量 shape | mask 不变量与数值对照 | 区分算术、带宽与激活内存瓶颈 |
| 生成与协议 | 调用模型输出 JSON | top-p、截断与校验测试 | 任务路由与成本/质量回归 |
| 数据与检索 | 构建索引 | 版本、ACL、召回诊断 | 更新删除、切换与漂移分析 |
| Agent 运行时 | 跑工具循环 | 授权、预算、失败恢复 | 副作用一致性与可审计恢复 |
| 服务与治理 | 跑题集或服务 | 分桶、负载与安全测试 | 门禁、事故响应与回滚演练 |

不要给每一行都追求 L3；应用负责人要能识别边界，深挖应集中在当前项目最关键的一两层。

## 2. 项目 A：可检查的微型语言模型

**任务：**用 PyTorch 构建小型 decoder，包含 tokenizer、embedding、位置方案、因果注意力、MLP、残差、词表投影和错位标签。使用自有或许可明确的小文本，不追求大模型效果。

<AiVisual title="微型模型先验收不变量，再比较架构" kind="layers" :nodes="[
  { label: '数据与标签', detail: '确认切分、padding 与错位标签，避免把数据问题当架构问题。' },
  { label: '注意力约束', detail: '因果 mask 保证当前位置不能偷看未来 token。' },
  { label: '生成路径', detail: '无缓存与有缓存输出应在容差内一致。' },
  { label: '可复现实验', detail: '固定输入、checkpoint 与单变量对照，记录真实测量。' }
]" caption="这些是不变量和实验设计，不是模型效果保证。" />

必须测试：改变未来 token 时过去位置 logits 不变；padding 不参与损失；无缓存/有缓存 logits 接近；保存加载 checkpoint 后固定输入可对照。小样本过拟合只说明训练链路工作，不能证明泛化。

::: details 实验与源码入口
一次只改位置方案、头数或上下文长度之一，记录验证损失、实际内存、计算时间与生成失败。可从 [nanoGPT](https://github.com/karpathy/nanoGPT) 或 [LLMs from scratch](https://github.com/rasbt/LLMs-from-scratch) 对照实现；教学仓库不是生产服务框架。
:::

## 3. 项目 B：可追溯的知识库更新

让团队助手支持制度新增、替换、撤回和租户权限变化，每个答案能回到当时使用的版本。

<AiVisual title="知识库更新的可追溯链" :nodes="[
  { label: '原始对象', detail: '保存文档版本、来源与解析状态，失败时可定位。' },
  { label: '索引快照', detail: 'chunk 与向量绑定版本，构建失败不覆盖可用快照。' },
  { label: '请求授权', detail: '根据当前身份选择可用版本，再做检索与重排。' },
  { label: '回答引用', detail: '记录证据版本；撤回与缓存失效需有明确语义。' }
]" caption="版本和 ACL 是数据契约的一部分，不是检索完成后再补的字段。" />

设计评审至少回答：新索引失败时旧索引是否继续服务；切换后缓存何时失效；删除要处理哪些向量、日志和备份；ACL 与缓存不同步时如何避免先泄漏。

::: details 失败注入实验
在构建、切换和删除的不同阶段注入失败，检查服务状态与审计记录；单独验证删除和撤权的完成条件。不要用“换一个向量库”代替生命周期设计。深入教程见 [RAG 生产化](../rag/10-生产化.md)。
:::

## 4. 项目 C：可恢复的受限工作流

先做低风险流程：查询资料 → 起草报告 → 用户确认后保存到测试目录，不启用外发邮件和真实业务写入。

<AiVisual title="恢复任务时，先判断副作用状态" kind="flow" :nodes="[
  { label: '保存状态', detail: '记录任务阶段、证据版本、预算、幂等键与待审批动作。' },
  { label: '中断恢复', detail: '重新校验当前身份、权限、资源和内容是否仍有效。' },
  { label: '核对结果', detail: '工具成功但记录未落库时，按幂等键查询，不盲目重做。' },
  { label: '安全停止', detail: '冲突、超预算或超时进入待核对，不能假报成功。' }
]" caption="“有日志”不等于具备一致恢复语义；真正写操作需由工具服务保证幂等与事务。" />

状态至少包括任务 ID、阶段、已完成步骤、预算、幂等键、工具结果引用和失败原因。人工批准隔很久后，旧批准不能无条件复用。可对照 [LangGraph](https://github.com/langchain-ai/langgraph) 与普通状态机实现，记录框架的收益和额外约束。

::: details 项目 D/E：什么时候增加 Agent 或部署优化
多 Agent 先与单 Agent 基线比较成功率、引用支持、总 token、耗时、交接丢失和合并失败；只有收益超过编排与校验代价才保留。部署报告至少记录请求数、成功/错误/超时、TTFT、端到端 p50/p95、吞吐、显存与质量回归。没有真实硬件时只做合成时间戳，并明确标注。
:::

## 5. 设计评审：拿证据讨论，而不是展示最好看的 Demo

1. 用户意图和允许的系统行为是什么？
2. 哪些输入不可信，哪些身份与授权由程序保证？
3. 每层输入输出和版本怎样记录？
4. 为什么选择此组件，简单替代是什么？
5. 哪类样本提升、哪类退化？
6. 质量、延迟、成本、安全怎样权衡？
7. 哪些是手算、合成、真实测量，哪些尚未验证？
8. 怎样回滚，谁负责剩余风险？

::: details 自测：能复现小实验就能负责生产系统吗？
不自动成立。生产还需要数据权限、稳定性、更新删除、监控、事故响应与组织治理；会部署成熟模型也不等于掌握训练原理。能力证据应分层陈述。
:::
