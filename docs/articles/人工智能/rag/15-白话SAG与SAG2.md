# 白话 `SAG` 与 `SAG2`：从相似片段到跨文档证据

“张三负责的项目，其客户的合同什么时候到期？”搜到一段介绍张三的文字，还不足以回答这个问题。我们要沿着“人 → 项目 → 客户 → 合同”找齐证据。

`SAG` 和 `SAG2` 都值得放在这个问题下理解：**后面该找什么，可能要等前一份资料出现才知道。** 本文使用虚构资料讲原理，核对日期为 `2026-11-27`；不把论文成绩当作本站实测。

## 1、先分清三个名字

| 名字 | 指什么 | 阅读依据 |
| --- | --- | --- |
| `SAG` | `SQL-Retrieval Augmented Generation`，采用事件—实体索引的检索架构 | [原论文 `v2`](https://arxiv.org/html/2606.15971v2) |
| `SAG2` | 采用词法索引、决策评分和查询时扩展的后续检索方法 | [后续论文 `v2`](https://arxiv.org/html/2610.22588v2) |
| `SAG-Wiki` | 使用 `SAG2` 的本地文件知识库应用 | [官方项目](https://github.com/Zleap-AI/SAG-Wiki) |

这三个名字分别涉及方法与应用。看到应用的版本号、安装包或截图时，先确认它实际使用的检索方法，不能把桌面版本号理解成论文版本号。

## 2、为什么相似的片段可能不够

准备三份虚构文档：

| 原文位置 | 内容 |
| --- | --- |
| `team.md` | 张三负责星河项目。 |
| `project.md` | 星河项目的客户是远帆公司。 |
| `contract.md` | 远帆公司的合同于 `2027-06-30` 到期。 |

最初的问题没有出现“远帆公司”。如果只用原问题检索一次，再把排名靠前的片段交给模型，第三份文档可能没进候选集。后面的回答模型再强，也不能从未拿到的证据中引用日期。

这并不说明向量检索必然找不到它。实际效果取决于文档、模型、切块和候选数。这个例子只是说明：**一次相关性排名没有显式要求系统找齐中间关系。**

```text
问题：张三负责的项目，其客户的合同何时到期？
  ↓ 查人和项目
team.md：张三 → 星河项目
  ↓ 以项目找客户
project.md：星河项目 → 远帆公司
  ↓ 以客户找合同
contract.md：远帆公司 → 到期日期
  ↓
回答，并绑定三处原文
```

## 3、`SAG`：先给资料建立可连接的索引

原始 `SAG` 将每个片段提取成一条保留整体含义的事件，并记录相关实体。事件—实体关联存入关系表，检索时通过共享实体的 `SQL JOIN` 扩展候选；它还使用向量等检索信号和模型筛选，最终回到原文片段。[方法说明](https://arxiv.org/html/2606.15971v2#S3)

把上述资料做成教学索引，可以是：

| 片段 | 事件 | 索引实体 |
| --- | --- | --- |
| `c1` | 张三负责星河项目 | 张三、星河项目 |
| `c2` | 星河项目的客户是远帆公司 | 星河项目、远帆公司 |
| `c3` | 远帆公司合同于指定日期到期 | 远帆公司 |

`c1` 与 `c2` 共享项目，`c2` 与 `c3` 共享客户，因此可以连接起来。所谓“超边”，可以先理解成一张同时关联多个人、项目、机构的资料卡；不必先掌握图论公式。

但“共享实体”只说明值得继续查。一份“星河项目旧版手册归档通知”也会命中项目名，却不能证明客户或合同到期日。**连接负责扩候选，证据筛选负责判断这段文字究竟证明了什么。**

`SAG` 名字里有 `SQL`，也不表示它只是让模型把自然语言翻译成数据库查询。这里关心的是如何组织文档检索索引，与查询现有业务报表的 `Text-to-SQL` 应区分开。

## 4、`SAG2`：把更多工作放到提问时

`SAG2` 在建索引时使用词法索引，不生成嵌入，也不让生成式模型预先抽取事件—实体结构。查询时，先用 `BM25` 找候选，再用决策模型判断片段对证据链的价值，从较好的候选中激活词项，继续查未访问片段。后续评分带上已检索上下文。[论文第 `3` 节](https://arxiv.org/html/2610.22588v2#S3)

继续用虚构例子理解：先拿到含“张三”的资料，发现“星河项目”；再拿着这个名字找项目资料，发现“远帆公司”；最后找客户合同。实际算法会保留多个候选和评分，不是每轮只选一张卡。

| 对照 | 原始 `SAG` | `SAG2` |
| --- | --- | --- |
| 建索引 | 提取事件、实体，并建立相关索引 | 建立词法索引 |
| 扩展桥梁 | 事件之间的共享实体 | 候选原文中激活的词项、名称 |
| 查询时筛选 | 模型选择候选证据 | 决策模型结合问题与上下文评分 |
| 两者共同要求 | 保留并返回原文证据 | 保留并返回原文证据 |

这个变化减少了预处理时依赖模型抽取的工作，但也把查找下一步证据的工作放到了查询阶段。是否适合自己的语料，仍要测首次可搜索时间、查询延迟和证据完整度。

## 5、决策模型与回答模型各做什么

在官方应用的说明中，`Jev` 负责判断证据价值，回答模型负责组织答案。`BM25` 则是依据词项匹配进行候选召回的排序方法，并不自己理解“这段话是否证明了客户关系”。[官方技术说明](https://github.com/Zleap-AI/SAG-Wiki/blob/b6940ac834b3b1ec651c0b49dc1b0c45d4d74c4a/docs-site/content/docs/sag2.en.mdx)

可以把职责写成三个问题：

1. 本地索引：哪些地方出现了这些词？
2. 决策模型：这份候选本身，能为原问题提供哪一步必要事实？
3. 回答模型：现有事实能否组成答案，哪些结论应引用哪些原文？

注意第二问的“本身”。`team.md` 证明张三负责哪个项目，不能因为上下文里有合同，就声称这份团队文档也证明了合同日期。有关联的候选不等于支持结论的证据。

站内的 [Jev 专题](/articles/jev/) 可以补充“结构化判断”与“自由文本生成”的差别；`SAG2` 则展示了判断模型在检索循环中的一个用途。

## 6、三个容易听错的结论

**“无向量就是全程无模型。”** 要区分阶段：建索引与快速搜索可以不调用模型；深度检索仍需决策服务；生成带引用的回答还需回答模型。外部服务是否收费、是否外发片段，取决于部署与配置。[应用使用条件](https://github.com/Zleap-AI/SAG-Wiki#user-guide)

**“第二代就能直接替换第一代的库。”** 方法变化不代表数据格式、接口或部署步骤兼容。升级前需要核对具体项目的迁移说明，不能仅凭名称替换依赖。

**“能找到更多材料，就能保证答案正确。”** 搜到错版本合同、同名客户或仅有背景关联的文字，仍会答错。最终要检查实体、时间、权限和原文是否支持结论。
