# `SAG` 关联检索最小实验：用 `SQLite` 串起三份证据

上一篇已经知道“张三 → 项目 → 客户 → 合同”需要多份原文。这里把连接过程写成一个可以运行和检查的程序。

**实验只演示原始 `SAG` 的共享实体关联思想。** 实体由我们手工标注，没有向量召回、自动抽取、模型选择或回答生成，因此不是原论文完整实现，也不是 `SAG2` 复现。`SAG2` 的差别放在第 `6` 节对照。

## 1、运行条件与入口

需要带 `sqlite3` 标准库的 `Python 3.10+`，不需要额外安装包、账户或密钥。程序使用内存数据库，固定加载虚构资料，不读取用户文档、不访问网络。

完整代码在仓库的 `docs/articles/人工智能/rag/examples/sag_sql_demo.py`。已经克隆本站源码时，在仓库根目录运行：

```sh
python docs/articles/人工智能/rag/examples/sag_sql_demo.py --test
python docs/articles/人工智能/rag/examples/sag_sql_demo.py --hops 0
python docs/articles/人工智能/rag/examples/sag_sql_demo.py --hops 1
python docs/articles/人工智能/rag/examples/sag_sql_demo.py --hops 2
```

`Windows` 如果用启动器管理版本，把 `python` 换成 `py`；其他环境可能使用 `python3`。自检正常时输出 `self-test: passed`。不要使用 `python -O` 跑自检，它会禁用 `assert`。

## 2、只保留两张表

本实验一条事件对应一段原文，所以直接用片段编号关联实体；独立的事件摘要表在这里没有必要。

```sql
CREATE TABLE chunks (
    id TEXT PRIMARY KEY,
    scope TEXT NOT NULL,
    path TEXT NOT NULL,
    body TEXT NOT NULL
);
CREATE TABLE event_entities (
    chunk_id TEXT REFERENCES chunks(id) ON DELETE CASCADE,
    entity TEXT NOT NULL,
    PRIMARY KEY (chunk_id, entity)
);
CREATE INDEX entity_lookup ON event_entities(entity);
```

`chunks` 保留原文和路径，`event_entities` 记录关联。`scope` 是教学用的可见范围，不是一套登录系统；真实服务必须从已验证身份计算可见范围，不能直接信任浏览器传来的字符串。

实验数据包含三份主资料和两个边界样本：

| 编号 | 范围 | 内容 | 用途 |
| --- | --- | --- | --- |
| `c1` | `public` | 张三负责星河项目 | 初始证据 |
| `c2` | `public` | 星河项目客户是远帆公司 | 桥接证据 |
| `c3` | `public` | 远帆公司合同于 `2027-06-30` 到期 | 目标证据 |
| `c4` | `private` | 远帆公司的保密报价 | 不应扩展进入公开结果 |
| `c5` | `public` | 星河项目旧版手册已归档 | 相关，但不能回答合同日期 |

## 3、一次 `JOIN` 完成一轮扩展

先精确查实体“张三”，得到种子 `c1`。从种子所在事件出发，找有相同实体的其他事件：

```sql
SELECT DISTINCT target.id
FROM event_entities source
JOIN event_entities linked ON linked.entity = source.entity
JOIN chunks target ON target.id = linked.chunk_id
WHERE source.chunk_id IN (?) AND target.scope = ?;
```

`source` 与 `linked` 是同一张关联表的两个别名：前者给出当前事件中的实体，后者找到所有使用这些实体的事件。范围条件在扩展查询内部执行，初始种子也使用同一范围。

完整代码按当前前沿的数量生成占位符，片段编号、范围、初始实体全部作为参数绑定；插入查询模板的只有程序生成的 `?`。去重集合记录已经访问的片段，下一轮只扩展新到达的部分，没有新片段就停止，最多允许 `5` 轮。

这是一种便于观察的广度扩展。它没有使用证据评分控制方向，因此候选会包含干扰资料。正式方法的候选预算和筛选不能被这个小例子替代。

## 4、观察每轮多了什么

| 参数 | 返回片段 | 观察 |
| --- | --- | --- |
| `--hops 0` | `c1` | 仅查种子，知道张三负责项目 |
| `--hops 1` | `c1`、`c2`、`c5` | 知道客户，也带入同项目的归档通知 |
| `--hops 2` | `c1`、`c2`、`c3`、`c5` | 获得合同日期，仍需筛掉无关证据 |

第二轮运行后的输出：

```text
[c1] team.md: 张三负责星河项目。
[c2] project.md: 星河项目的客户是远帆公司。
[c3] contract.md: 远帆公司的合同于 2027-06-30 到期。
[c5] archive.md: 星河项目的旧版手册已归档。
```

结果按编号排序，方便阅读，不代表模型相关性排名。程序返回原文，并没有生成自然语言答案。

现在手工检查问题：`c1` 证明负责人关系，`c2` 证明客户关系，`c3` 给出日期，`c5` 无须放进最终引用。`c4` 虽然共享客户名，也不能越过可见范围进入候选。

## 5、自检具体证明什么

脚本里的 `self_test()` 检查：

1. 初始种子、第一轮和第二轮的片段编号符合预期。
2. 已访问片段不重复返回，继续增加轮数不会在环中无限运行。
3. 公开检索不会进入私有报价；私有范围不能借公开种子继续扩展。
4. 不存在的实体以及含引号和注入形式的输入返回空集；空实体和越界轮数被拒绝。
5. 每条结果保留原文与路径；删除桥接片段 `c2` 后，合同 `c3` 不再能从张三到达，外键级联清理关联行。

这些断言验证的是连接、边界和数据一致性。它们不证明中文实体抽取准确、同名公司能正确消歧、检索质量优于别的方法，也不证明线上权限系统已经实现。

可以继续做两个手工实验：把客户名写成简称，观察精确连接如何断开；增加一份同名客户的旧合同，观察连接结果为何不能直接决定答案。两者分别暴露别名规范化和版本筛选的问题。

## 6、同一个例子，换成 `SAG2` 会改哪里

上面先写入“片段—实体”关系，查询时再连接。`SAG2` 则先建立词法索引，在查询时从候选文字中挑选扩展词，并结合证据上下文重新评分。[官方技术说明](https://github.com/Zleap-AI/SAG-Wiki/blob/b6940ac834b3b1ec651c0b49dc1b0c45d4d74c4a/docs-site/content/docs/sag2.en.mdx)

用这个虚构数据集做一次**人工推演**，而非真实运行记录：

| 阶段 | 可能的操作 | 必须核验 |
| --- | --- | --- |
| 初始召回 | 通过问题中的人名等词项找候选 | 是否拿到 `c1` |
| 证据判断 | 判断 `c1` 对负责人关系是否必要 | 不能因为没有日期就丢掉中间证据 |
| 第一次扩展 | 从候选中获得“星河项目”再检索 | `c2` 与 `c5` 哪个提供必要关系 |
| 后续扩展 | 使用“远帆公司”等桥接词找新候选 | 范围内能否找到有效合同 |
| 最终评分 | 结合上下文重新判断候选的作用 | 每一段只能支持自身原文中的事实 |

若要实现 `SAG2`，需要真正接入并校准决策模型，补齐词项激活、候选预算、上下文和最终排序。这里不写一个按文档编号返回固定高分的假评分器，因为那只能重演我们预先写好的答案。
