# `SAG` 与 `SAG2` 对比及选型：把召回、成本和证据分开看

读完前两篇，我们知道了连接怎样帮助检索。接下来的问题是：**为了自己的文档和问题，是否值得更换现有链路？**

本文截至 `2026-11-27` 核对公开资料。结论分三类：论文和项目报告的事实、本站教学程序验证的行为、需要自己执行的评估。没有执行过的测试不填写成绩。

## 1、先定位失败，再选方法

| 当前现象 | 先检查 | 候选改动 |
| --- | --- | --- |
| 合同根本没有入库 | 解析、索引状态、范围过滤 | 修摄取链路 |
| 用简称搜不到公司全称 | 分词、别名、查询改写 | 补词法与语义召回 |
| 只找到负责人，没找到客户合同 | 桥接证据是否进入候选 | 多轮检索或结构关联 |
| 材料齐全，却用旧合同回答 | 版本、时间、筛选与引用 | 修证据约束 |
| 需要汇总全公司的项目主题 | 全局覆盖与聚合方法 | 评估分层摘要或图谱方案 |

这是一张排查建议表，不是方法优劣排名。尚未入库的文档无法通过更复杂的检索恢复；原文没有记录的合同日期，也不能靠多跳搜索补出来。

## 2、比较架构，不把名字当能力清单

下表中的“向量 `RAG`”特指一次向量召回再生成的基础流程；实际系统可以加入词法召回、重排和迭代检索。`GraphRAG` 实现也各有差异。

| 路线 | 离线主要工作 | 查询时主要工作 | 值得验证的场景 |
| --- | --- | --- | --- |
| 基础向量 `RAG` | 切块、嵌入、索引 | 相似片段召回，再生成 | 语义表达变化大、单段可回答 |
| `GraphRAG` | 建立实体关系及可能的社区摘要 | 局部关系或全局聚合检索 | 关系分析、语料层面的总结 |
| 原始 `SAG` | 事件—实体抽取、相关索引 | 共享实体扩展、候选选择 | 中间实体明确的跨文档证据链 |
| `SAG2` | 词法索引 | `BM25`、决策评分、词项扩展 | 更新频繁、需跨文档追证的资料 |

`GraphRAG` 的全局聚合用途可对照 [Microsoft 官方说明](https://microsoft.github.io/graphrag/)。两代 `SAG` 的方法边界分别见 [原始论文](https://arxiv.org/html/2606.15971v2) 和 [后续论文](https://arxiv.org/html/2610.22588v2)。这些“值得验证的场景”是根据机制提出的选型建议，不是作者已证明适用于全部同类业务。

## 3、`SAG2` 的三个阶段不能混算

| 阶段 | 可做什么 | 模型参与 |
| --- | --- | --- |
| 建索引 | 解析、切分、词法索引 | 方法不要求生成式模型抽取或嵌入 |
| 深度检索 | 找候选、判断证据、继续扩展 | 决策模型参与判断 |
| 问答 | 把证据组织成回答并引用 | 回答模型参与生成 |

官方应用还提供本地快速搜索，与使用决策模型的深度检索是不同工作流。[应用技术说明](https://github.com/Zleap-AI/SAG-Wiki/blob/b6940ac834b3b1ec651c0b49dc1b0c45d4d74c4a/docs-site/content/docs/sag2.en.mdx)

所以比较费用时，应分别记录首次索引、增量更新、查询评分和答案生成。一个查询有几轮检索、每轮多少候选、是否分批评分，也会影响请求次数。不能把“一次工具调用”直接记成“一次模型请求”。

## 4、怎样读官方成绩

`SAG2` 论文 `v2` 在三个各含 `1,000` 个问题的子集上报告证据 `Recall@10`：`MuSiQue` 为 `86.62%`，`2WikiMultiHopQA` 为 `97.43%`，`HotpotQA` 为 `99.00%`。这些是作者在指定配置下的检索结果，**不是本站复现，更不是回答正确率**。[论文与实验设置](https://arxiv.org/html/2610.22588v2#S4)

假设一道题需要 `3` 段证据，只找到 `2` 段，按证据数量计算的召回比例是 `2/3`，但完整证据链仍然缺一环。这就是为什么还应记录“全部必要证据是否齐全”。如果业务需要合同生效日期、负责人和金额三个事实，缺任何一个都可能导致错误决策。

评估时至少分清：

1. 证据 `Recall@k`：标注证据找回了多少。
2. 完整证据链命中率：每道题需要的证据是否全部找到。
3. 引用支持率：回答里的结论能否由对应原文支持。
4. 最终答案正确率：事实、范围与时间条件是否都正确。

产品页面、论文版本和基准仓库可能采用不同设置。先检查数据子集、切块、评分后端、候选预算、扩展次数及是否加入 `Agentic` 扩展，再判断数字是否可以比较。[官方复现说明](https://github.com/Zleap-AI/SAG-Benchmark/tree/bb7f82751ba1576219f9d9ebd021128603d130c3/sag2)

## 5、给自己准备一组小而真实的题

下面是一份建议实验，尚未执行；起步可准备 `30` 道题，每类 `5` 道。真实资料需使用有权处理的脱敏副本。

| 类型 | 示例 | 观察重点 |
| --- | --- | --- |
| 单段事实 | 某合同的到期日 | 基础召回能否做好 |
| 词面变化 | 客户简称对应哪份合同 | 别名、缩写、语义差异 |
| 跨文档关联 | 某负责人项目客户的合同日期 | 桥接片段与完整链 |
| 时间冲突 | 去年与今年合同哪个有效 | 版本与日期条件 |
| 无答案 | 资料没有记载的审批人 | 拒答与引用约束 |
| 可见范围 | 当前身份看不到的项目 | 任一扩展阶段是否越界 |

固定同一语料版本和标注，先比较已有检索与新检索的原文结果。随后用同一个回答模型和提示词生成答案，才便于区分改进来自检索还是生成。允许各方法采用原生索引，但要记录切块和去重粒度，避免拿段落召回与文档召回直接比较。

建议的记录表如下；空白表示待测，不填估计值：

| 指标 | 当前链路 | 原始 `SAG` | `SAG2` |
| --- | --- | --- | --- |
| 证据 `Recall@10` | 待测 | 待测 | 待测 |
| 完整证据链命中率 | 待测 | 待测 | 待测 |
| 首次建索引耗时 | 待测 | 待测 | 待测 |
| 增量更新耗时 | 待测 | 待测 | 待测 |
| 查询延迟中位数 / `P95` | 待测 | 待测 | 待测 |
| 每题模型费用与请求数 | 待测 | 待测 | 待测 |
| 越权命中 / 删除残留 | 待测 | 待测 | 待测 |

对同一组问题重复测量，报告运行次数和波动。`30` 道题适合找明显失败，不足以宣称普遍领先。

## 6、与站内已有内容如何连接

基本检索和重排见 [06 检索与重排](./06-检索与重排.md)；指标和门禁见 [09 评估](./09-评估.md)；部署边界见 [10 生产化](./10-生产化.md)。两代方法不会免除这些工作。

代码阅读建议从官方 `SAG-Wiki` 的 `core/src/retrieval.rs` 看候选与检索循环，再看 `core/src/sag2_v10.rs` 的评分准则、词项处理与多样性排序。评分准则强调当前候选自身提供必要事实，不能把其他上下文的事实算到它名下。[固定提交的源码](https://github.com/Zleap-AI/SAG-Wiki/blob/b6940ac834b3b1ec651c0b49dc1b0c45d4d74c4a/core/src/sag2_v10.rs)

如果已经部署知识库，先导出一组失败问题做旁路评估。只有当新方法补齐了重要证据，并且延迟、费用和维护成本可接受，再考虑替换链路。
