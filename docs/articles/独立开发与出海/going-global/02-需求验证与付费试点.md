# 需求验证与付费试点：把产品想法变成可核对的证据

做独立产品时，最昂贵的错误往往不是技术选错，而是花几个月解决一个用户并不急着处理的问题。本篇接续[入门总览](./01-AI出海副业从0到1实战指南.md)，把“先验证需求”拆成能执行的研究和试点流程。

**本篇交付物**：一张需求证据表、一组访谈记录、一份试点约定，以及继续或停止的决定。贯穿案例仍是客户反馈整理器，所有客户与数字均为教学假设，不是已发生的交易。

> **视频跟练**：先看 [用户访谈方法课](https://www.youtube.com/watch?v=z1iF1c8w5Lg)；想找带中英标注的入口，可参考 [`Bilibili` 第十六讲](https://www.bilibili.com/video/BV14gvKzYEhN/)。它们不是同一集，也不是屏幕操作教程。看后完成一次明确标为模拟的访谈训练，保存提纲、记录及诱导问题改写；[具体任务与核验边界](./10-视频跟练与项目实操路线.md#_2-用户访谈-先听问题-再展示产品)见跟练页。

## 1. 先缩小人群，再讨论功能

### 1.1 用角色、事件和结果定义市场

“面向海外的效率工具”不是可访谈的人群。可操作的定义是：

> 面向每周从客服记录中整理产品反馈的小型软件团队，帮助负责整理的人把获授权的反馈转换成带原文来源的主题清单，交给产品负责人审核。

这里包含使用者、发生频率、输入和结果，但还没有证明存在需求。还要区分三个角色：谁整理、谁采用结果、谁批准购买。同一个人可能兼任，也可能需要跨部门审批。

先选择一个自己能接触的群体，而不是先估算全球有多少开发者。市场规模很大，不能弥补你没有合法、可重复的接触渠道。

### 1.2 为每个方向建立反证

| 假设 | 支持它需要什么 | 什么证据会让你放弃 |
| --- | --- | --- |
| 整理反馈很费时间 | 最近几次任务的具体步骤和工时 | 大部分目标团队几乎不做这件事 |
| 来源追溯值得付费 | 审核时确实反复回查原文 | 用户只需要粗略摘要，免费方案已够用 |
| 任务会重复 | 能指出下一次整理的时间或触发条件 | 只在偶发项目中使用一次 |
| 能成交 | 有预算、批准人和允许的采购路径 | 数据政策禁止上传，且没有可行替代方案 |

不要只搜支持自己想法的帖子。主动记录反例，包括“现在的方法很好”“不愿换工具”“没有数据授权”。反例决定产品边界，比收藏更多成功故事更有价值。

## 2. 研究替代方案，而不是列一张竞品功能表

用户的替代方案可能是表格、实习生、咨询服务，甚至“不处理”。真正的比较是完成同一项工作的总成本，而不是谁的按钮更多。

建议先查看少量有代表性的工具和公开评价，再在访谈中确认它们是否真的被使用。遵守站点访问规则，不复制付费资料、不伪造注册身份，也不把公开评价当作已经获得的数据处理授权。

```text
替代方案名称：
用户用它完成哪一步：
进入条件与数据要求：
可观察的价格和限制；记录日期：
用户实际称赞和抱怨的内容：
迁移要重新整理哪些数据：
我们的差异能否在一份样例里证明：
仍然未知、必须通过访谈确认的事项：
```

**迁移成本要单独问**。新工具即使处理快，也可能要求转换文件、学习格式和向同事解释。反馈整理器应比较“准备输入＋运行＋核对＋修正＋交付”的总时间，不能只展示生成结果用了多少秒。

## 3. 访谈时，把推销与学习分开

`YC` 的用户访谈资料强调：问生活和问题、问已经发生的具体事情，而不是让对方预测是否会购买未来功能，详见来源 `S1`。下面是适配独立开发者的访谈流程，不是官方规定的次数或标准。

### 3.1 招募与告知

从允许交流的行业社区、已有关系或对方公开提供的适当商务入口招募。说明自己在研究什么、需要多长时间、是否录音以及如何使用记录。录音需得到适当同意；不需要录音时，用脱敏笔记即可。

可以先约 `5` 次不同角色的交流。这是降低启动成本的操作目标，不是“访谈够数就验证成功”。如果始终找不到相关受访者，应先解决用户可达性，不是继续开发。

### 3.2 一次访谈的顺序

1. **回放事件**：“最近一次整理反馈是什么时候？为什么那天要做？”
2. **还原工作流**：“能按顺序讲一遍吗？哪些步骤要交给别人？”
3. **找实际损失**：“哪里返工最多？没整理会影响什么？”
4. **核对替代方案**：“尝试过哪些工具？上次为什么没有继续用？”
5. **确认购买与数据约束**：“谁能批准试点？是否允许外部处理样本？”
6. **约定下一步**：“如果你愿意，我们能否用脱敏样本比较一次结果？”

前半段不要展示界面。否则用户容易顺着你的设计讨论颜色和功能，而不再讲自己的真实工作。后半段可以展示样例，但要明确哪些是已实现、哪些是人工处理、哪些尚不支持。

### 3.3 区分事实、推测和承诺

| 记录类型 | 示例 | 能否直接支持投入 |
| --- | --- | --- |
| 具体经历 | 上周为了周会，整理了两个来源的反馈 | 可以支持任务存在，仍需了解频率与成本 |
| 用户解释 | “最烦的是来回找原文” | 是价值线索，最好结合实际操作确认 |
| 泛泛评价 | “这个想法挺好” | 不能证明采用或付款 |
| 行动承诺 | 约定下周提供获授权样本，邀请付款决策者 | 比评价更强，但仍不等于实际成交 |
| 实际交易与复用 | 按约付款、采用结果、下轮任务再次使用 | 是更强证据，仍不能代表整个市场 |

整理记录时保留用户原话，但不要把原话改成产品宣传。公开引用、展示公司名称或标志，应另行获得相应许可。

## 4. 先做一次人工交付，明确什么值得自动化

`Paul Graham` 关于不可规模化工作的文章指出，早期可以手动招募、服务用户，甚至先人工完成后来要自动化的工作，见来源 `S2`。这是一种探索方法，不保证你的方向一定成立。

对反馈整理器，先约定一份格式固定、已脱敏的样本，人工整理主题和来源，然后请对方在实际审核中指出：

- 哪些主题确实被采用，哪些合并错了？
- 找原文是否更方便，是否仍要重新做一遍？
- 输出要交给谁，怎样才算完成交付？
- 下一轮是否愿意按相同范围继续？

把人工耗时分成输入清理、分类、核对和交付。只有重复出现且规则较稳定的部分，才值得优先自动化。不要把一名客户的全部定制流程直接升级成通用平台。

## 5. 从试用转为边界清楚的付费试点

### 5.1 试点约定模板

```text
试点对象与付款主体：
需要完成的工作，以及不包含的工作：
输入格式、数量、大小和授权要求：
交付形式、时间与人工参与程度：
客户验收方式、修改轮次与失败处理：
价格、税费展示与允许的收款渠道：
取消、退款及争议处理：
数据接收方、访问范围、保存与删除时间：
双方联系渠道与下次复盘时间：
能否使用评价、名称或样本做宣传：默认不授权，另行确认。
```

这不是法律合同范本。涉及保密、知识产权、个人数据或跨境处理时，应根据实际情况取得专业意见。人工服务是否属于收款平台允许的商品，也要单独确认，不能因为未来准备做软件就按软件销售规则收费。

### 5.2 定义“成功”与“付费”的关系

一次试点可以先约定“结果中每个主题能找到对应来源，用户完成审核并确认可交付”。不能把“生成了一份文件”当成客户成功，也不应以模糊的“保证业务增长”作为验收。

如果收款尚未获批，可以做清楚标注的免费研究或沙箱演示，记录试点意愿，**不能把它称为已经获得付费验证**。付费试点应按平台允许的真实交易完成，不做自刷或关联人虚假购买。

## 6. 复盘：下一步只能由证据决定

| 观察结果 | 更合理的下一步 |
| --- | --- |
| 有重复任务、结果被采用，但整理格式很难准备 | 优先降低输入门槛，再验证一次 |
| 有人愿意用，但付款者认为免费工具足够 | 重新验证差异和采购路径，不只做促销 |
| 只有一家要求大量定制且任务不重复 | 判断是否做有边界的服务，不假装已验证通用产品 |
| 有付款，却没有下一轮需求 | 先按一次性产品经营，不急着做订阅 |
| 多轮交流仍拿不到具体事件或下一步 | 暂停当前方向，换人群或问题 |

早期样本应同时看正面和负面个案，不用几次交流计算“市场成功率”。没有统一的访谈次数、付费人数能自动证明产品适配市场。

### 本篇验收清单

- [ ] 能说清使用者、结果采用者和付款决策者。
- [ ] 记录了最近发生的任务，以及至少一种真实替代方案。
- [ ] 保留了反例，没有把客气评价算成成交。
- [ ] 样本授权、人工参与、交付与退款边界明确。
- [ ] 试点结束后有采用记录、费用和下一次任务判断。
- [ ] 已写下继续、调整或暂停的理由，而不只是功能待办。
