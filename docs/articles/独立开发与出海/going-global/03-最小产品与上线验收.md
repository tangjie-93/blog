# 最小产品与上线验收：先交付一条可靠的用户路径

[上一篇](./02-需求验证与付费试点.md)解决“是否值得做”，本篇解决“第一版做到哪里才可以交给真实用户”。`MVP` 不是功能最少的半成品，而是能用有限投入验证关键假设的产品版本；安全、诚信和收费责任不能被当作可以删掉的功能。

**本篇交付物**：一页范围说明、一份验收矩阵、一次受控发布记录。以客户反馈整理器为教学案例，不限定框架，也不要求产品必须使用 `AI`。

> **视频跟练**：先看 [静态网站部署演示](https://www.bilibili.com/video/BV1kX4y1v75w/)，完成测试页发布、更新和回退；再按 [`Supabase` 教程的认证、数据库和存储分集](https://www.bilibili.com/video/BV1GD7GzUExH/?p=3)完成双账号任务隔离。旧视频的免费套餐与界面不作当前承诺；[分集入口、成果和核验说明](./10-视频跟练与项目实操路线.md#_3-部署和数据-做出自己的最短闭环)见跟练页。

## 1. 第一版只承诺一个完整结果

### 1.1 从用户任务倒推最短路径

反馈整理器的第一版路径可以是：

1. 用户确认输入要求，上传获授权的反馈表。
2. 系统检查格式和用量，创建属于该用户的任务。
3. 完成处理，提供能追溯原文的主题草稿。
4. 用户核对并导出，或看到明确的失败与补偿说明。
5. 用户能查看任务记录、联系支持并申请删除数据。

“完整”指正常和失败情况下都能交代结果，不是把团队协作、外部集成、主题市场都加上。早期人工协助可以存在，但必须说明参与程度和可服务时间，不能把人工代做宣传为全天自动交付。

### 1.2 范围说明要写“不做什么”

| 范围 | 第一版决定 | 重新评估的触发条件 |
| --- | --- | --- |
| 输入 | 只接受模板规定的 `CSV` | 多位目标用户证明转换格式成为主要阻塞 |
| 输出 | 主题、来源编号、摘要和可编辑草稿 | 用户确实需要另一种固定交付格式 |
| 账号 | 单人使用，不支持共享登录 | 出现真实的团队采购与成员管理需求 |
| 自动操作 | 不向外部系统写入内容 | 已有明确授权、撤销和审核方案 |
| 收费 | 先验证一种明确额度的商品 | 任务频率与复购支持更复杂套餐 |

“以后可能有人要”不是触发条件。需求变更应关联真实证据，并写出因此放弃的工作，避免每次访谈都往第一版里加一个模块。

## 2. 数据契约比界面细节更早确定

### 2.1 让输入、输出和限制可核对

为反馈表规定必填列、字符编码、最大行数、单条长度和重复编号处理方式。错误应指出具体问题，不静默丢行后宣称处理完成。

输出中保留 `source_id` 对应关系。主题的条数应按程序规则计算；允许一条反馈属于多个主题时，要说明分类计数可能重叠。对无法判断的材料显示待复核，而不是补出不存在的事实。

```text
输入契约版本：
接受的文件、必填列与限制：
重复项、空值、编码错误的处理：
输出字段与来源追溯规则：
用户能修改什么，导出包含什么：
预计耗时范围与超时条件：
不支持的内容与人工复核要求：
删除、保留与备份处理规则：
```

给契约一个版本，方便解释为什么旧任务与新任务存在差异。第一版并不一定要建设复杂的版本系统，一份随发布记录保存的说明就能起步。

### 2.2 列出数据实际经过的地方

至少画清或写清“浏览器、应用服务、文件存储、数据库、外部处理方、日志与备份”。逐处回答保存哪些数据、谁能访问、何时删除。

页面写“立即删除”，但后台任务、对象存储和日志继续保留原文件，就是产品承诺与实现不一致。备份是否支持即时逐项删除也必须说明，不能用删除数据库记录替代全链路处理。

## 3. 让任务有明确状态，而不是一直转圈

建议先定义以下业务状态，再实现界面。具体名称是教学设计，不是某个平台的固定接口。

| 状态 | 允许发生什么 | 用户看到什么 |
| --- | --- | --- |
| `queued` | 排队，尚未开始 | 排队说明、合理的取消入口 |
| `running` | 正在执行，按规则限制并发 | 当前阶段与可接受的等待提示 |
| `succeeded` | 结果校验通过并可读取 | 结果、来源与导出 |
| `failed` | 已停止，记录可排查的错误分类 | 是否能重试、额度怎样处理 |
| `canceled` | 已确认停止，不再交付结果 | 取消结果及可能已产生的消耗 |

**取消请求不等于底层计算已经停止**。如果执行器无法马上终止，应先显示取消处理中，待确认后结束状态；已经发生的费用按事前政策处理。

重复点击、断网重连和自动重试不应无限创建新任务。为一次操作保留稳定的请求标识，约束重复创建和重复扣减。处理超时后，还要考虑外部服务稍后返回结果的情况，避免同一任务同时被记为失败和成功。

## 4. 用验收矩阵代替“我点过一遍”

### 4.1 最小测试集合

| 场景 | 必须观察到的结果 |
| --- | --- |
| 正常样本 | 结果来源合法、可核对、可导出 |
| 空文件或格式错误 | 拒绝并给出修复提示，不生成假成功 |
| 超过输入上限 | 清楚说明限制，不静默截断 |
| 同一次提交重复请求 | 按约复用任务或拒绝重复，不重复收费 |
| 执行器失败或超时 | 进入可解释状态，权益按规则补偿 |
| 刷新、断网后重开 | 可以恢复查询，不依赖当前页面内存 |
| 用户甲查询用户乙的任务 | 服务端拒绝，结果与下载地址不泄露 |
| 旧任务导出或删除 | 仍校验身份和归属，而非只检查创建时 |
| 回滚到上一版本 | 已有数据可读，不因字段不兼容损坏 |

权限检查应遵循默认拒绝、最小权限和每次请求验证原则，依据来源 `S1`。隐藏按钮、使用难猜的编号、添加登录页面，都不能代替服务端授权。双账号测试要覆盖读取、下载、删除和后台任务状态，不只测列表页。

### 4.2 区分“发布阻断”与“以后改进”

以下问题应阻断收费或扩大试点：跨用户数据可见、价格或额度计算错误、失败无法追踪、关键数据无法恢复、隐私说明与实际不符。

可以后续改进的内容包括动效、更多配色、非必要筛选和不影响交付的排版。不应该用“再补一个功能”覆盖当前已发现的严重缺陷。

## 5. 成本、备份和回滚也是产品能力

### 5.1 设真正能执行的资源上限

逐项写出文件限制、单用户速率、并发、最长运行时间、最大重试次数和总预算。区分两种机制：

- **告警**：告诉你费用或错误异常；你不在电脑前时，它不会自动停止消耗。
- **硬限制**：拒绝新增工作、暂停高成本功能或停止试用；也要向用户说明现状。

仅限制每个账号不足以防止共享资源耗尽。还需总队列、供应商配额和异常用量的保护，避免一个后台重试循环拖垮全部用户。

### 5.2 实际恢复一次，而不是只看备份开关

选择隔离环境，用不含真实敏感内容的样本验证：能恢复任务、文件和必要配置，结果可读且权限仍然正确。记录可接受的数据损失窗口，即 `RPO`，以及恢复服务所需时间目标，即 `RTO`。它们是自定目标，不是打开备份后自动获得的保证。

`Supabase` 官方文档明确，数据库备份不包含通过 `Storage API` 保存的对象本身，见来源 `S2`。即便使用其他平台，也应逐项确认备份范围，不能把数据库恢复等同于整个产品恢复。

## 6. 受控发布：先让少量用户完整用一次

1. **冻结范围**：保存本次功能、已知限制、价格与数据契约。
2. **隔离环境**：测试与生产使用不同的凭据、数据和支付环境。
3. **完成验收**：逐条留存通过或失败记录；不通过的阻断项先修复。
4. **小范围开放**：邀请已沟通并了解限制的试点用户，说明可支持时间。
5. **观察完整交付**：从进入页面到采用结果，而不只看服务有没有报错。
6. **决定扩大或回滚**：以用户影响与恢复能力为准，不用发布日程强推。

每次发布记录时间、版本、迁移事项、回滚步骤和观察结果。数据库迁移尤其要确认向后兼容；代码回滚并不自动撤销数据结构变更。

### 本篇验收清单

- [ ] 第一版有单一结果和明确不做清单。
- [ ] 输入、输出、失败与删除契约已写清。
- [ ] 双账号授权、重复请求和超时测试通过。
- [ ] 告警与硬限制都已验证，能停止新增高成本任务。
- [ ] 备份范围明确，隔离环境已完成恢复演练。
- [ ] 正常路径、失败补偿和回滚都有记录。
