# 海外收款与支付状态机：从商户审核到人工对账

上一篇：[最小产品与上线验收](./03-最小产品与上线验收.md) · 下一篇：[定价与单位经济模型](./05-定价与单位经济模型.md)

收款上线的标准不是出现付款按钮，而是每笔钱都能解释：谁付的、买了什么、权益发了几次、退款后剩多少、何时进入自己的账户。本文延续“客户反馈整理器”教学案例，只讨论经营与状态设计，不涉及模型接口实现；套餐与政策均为待验证假设，不代表真实交易或试验结果。

> **视频跟练**：[使用 `Paddle` 与 `Next.js` 接入支付](https://www.youtube.com/watch?v=ot5BrFCjo8c)是英语第三方操作演示；本轮只核对搜索索引中的简介和章节。先练沙箱商品与支付通知，再补重复事件、坏签名和退款测试，不涉及正式收费；[章节定位、任务与验收](./10-视频跟练与项目实操路线.md#_4-沙箱支付-不要停在-成功页出现了)见跟练页，不能用视频代替商户审核。

## 1. 先做准入判断，不先接按钮

**卖家准入、买家支付、资金结算是三个不同问题。** 海外客户能刷卡，不表示你的主体能开户；沙箱成功，也不表示正式账户获批。

1. 填写真实经营地、主体类型、软件交付内容、买家地区和本人或企业名下的结算账户，向候选平台确认资格。个人是否可申请、账户是否可收款，必须分别询问。
2. 阅读商品限制，确认售卖的是软件，而非把人工咨询包装成软件。未获准时只做演示和沙箱，不承诺正式收款日期。
3. 准备可访问的网站，写清功能、价格、输入限制、交付、联系渠道、隐私、退款和服务条款，再提交审核。

截至检索日，`Stripe Global` 商户开放名单列有香港，未列中国内地；页脚语言选择器中的“中国内地”不是开户名单。它讨论商户所在地，而非所有买家所在地区。[来源一](#来源一)

`Paddle` 官方商户排除名单未列中国，但正文同时保留风险审查和补充资料要求；这不是个人、商品或结算账户必过的保证。域名审核还要求明确的产品说明、价格、政策和安全访问，可能索取测试账号；身份及主体审核不能被域名通过替代。[来源二](#来源二)

不要伪造地址、借身份、买账号或隐藏经营地区。资格不满足时，应暂停收费并咨询合规方案，而不是寻找绕地区的接入教程。

## 2. 单独核对迁移、税务和结算

旧指南中的 `Lemon Squeezy` 日期，本轮从官方迁移正文重新确认：`2026-11-16` 已停止接受新用户和新店铺；`2027-03-31` 将停止处理交易，**包括订阅续费**。因此不把它作为新项目开户选项。公告推荐的 `Stripe Managed Payments` 仍有所在地、商品和功能资格限制，不是所有旧商户自动可用。[来源三](#来源三)

已有商户应先导出订单、客户、订阅和余额记录，再建立新旧编号映射，核对取消日期与下一次扣费，避免双重续费。按公告，结账链接和集成不会自动重定向；迁移不是仅替换首页按钮。完成买家通知、沙箱回归和双方状态核对后才切换。

`Merchant of Record`，简称 `MoR`，指平台作为法律上的转售方承担相关交易税处理。`Paddle` 官方说明覆盖销售税和增值税，并非宣布卖家免税。自身所得、会计、开票、外汇及本地申报仍需按主体咨询专业人士；合同也保留卖家自身合规义务。[来源四](#来源四)

另建一张结算记录，填写周期、门槛、币种、汇兑、银行费、退款扣减及审核留置。`Paddle` 帮助页目前描述按月结算、最低门槛 `$100`，低于门槛结转；实际以账户设置、合同与风控结果为准。付款成功、平台余额和银行到账必须分列，不能把“已发送”当作银行已入账。[来源五](#来源五)

## 3. 为反馈整理器拆出三套状态

先卖有边界的处理额度包；只有确认任务持续发生，再增加月订阅。将支付事实、服务权限、额度数量分开保存，不用一个“会员有效”字段解释全部业务。

| 对象 | 教学状态或流水 | 关键约束 |
| --- | --- | --- |
| 支付订单 | 待付款、已确认、部分退款、全额退款、争议中 | 退款是后续记录，不抹掉原交易 |
| 订阅权限 | 试用、有效、逾期、暂停、取消 | 保留当前服务期与计划变更生效时间 |
| 额度账本 | 发放、预留、消耗、释放、退款冲回 | 每条记录能定位订单、任务和原始流水 |

订阅状态可映射 `Paddle` 的 `trialing`、`active`、`past_due`、`paused`、`canceled`。官方规定期末取消通过计划变更表达，生效前状态不一定变为取消；不能收到取消申请就立即收回已付服务。[来源六](#来源六)

本例自定政策是：试用单列额度；付费周期经交易确认后仅发放一次；逾期不发下一期新额度，保留已付权益并提示更新付款方式；暂停或取消生效后停止新处理，保留约定的只读导出。该政策须事先披露，不是平台强制规则，退款也不自动等于取消订阅。

额度包假设包含 `30` 次有输入上限的处理。任务开始先预留一次，成功后消耗，失败则释放；重试沿用同一任务标识，不再扣一次。订阅发放以“订阅编号与服务期”唯一，额度包以交易编号唯一，避免不同事件为同笔购买重复发放。

## 4. 按顺序处理支付通知

1. 读取未经改写的原始请求体，使用对应环境、通知地址的密钥验证 `Paddle-Signature`，并检查签名时间容差。解析再重新序列化可能验签失败；不以浏览器成功页作为发放依据。[来源七](#来源七)
2. 验签后先可靠落库或进入持久队列，再确认接收。`Paddle` 要求在 `5` 秒内返回 `HTTP 200`；若无法可靠接收，应让其重试，不做“先返回成功、内存里慢慢处理”。[来源八](#来源八)
3. 以 `event_id` 去重，并记录接收、待处理、成功、失败。官方保证至少一次投递，事件与通知编号不是同一概念。处理失败可重试，不能因为编号存在就永久跳过。[来源八](#来源八)
4. 后台校验商品、金额、币种、环境及订单所属用户，在同一数据库事务中提交额度流水和处理成功标记。唯一约束负责挡住并发重复，不只靠事前查询。
5. 对同一订阅比较 `occurred_at`，不用到达时间覆盖状态；出现同时间冲突、缺失或矛盾时查询平台当前对象再裁决。旧事件仍可能含未记账交易，不能因时间较早便丢弃全部经济事实。[来源八](#来源八)

发起付款或退款请求时也需防重复：先生成业务操作编号，超时后查询结果，只有确认未成功才重试；平台支持请求幂等键时按其文档使用。请求幂等和通知去重解决的是不同方向的问题。

## 5. 演练退款、乱序与人工补偿

| 错误场景 | 正确处置与验收证据 |
| --- | --- |
| 同一通知重放或并发到达 | 只有一条购买发放流水，保留重复接收记录 |
| 先到取消事件，后到旧的有效事件 | 不恢复过期权限，状态能与平台查询结果一致 |
| 钱已付，额度处理失败 | 后台可重试；人工通过原订单补发，不另造购买 |
| 请求退款后连接超时 | 查询平台结果，未确认前标记待核对，不重复退款 |
| 部分退款且额度已使用 | 按已披露政策及法定权利核算；不足以冲回时转人工，不静默扣成负数 |

退款要保留申请、平台确认和失败记录；确认后写关联原购买的冲回流水，不删除历史、不擅自擦除客户数据。全额退款、部分退款和争议分别处理，是否取消续费另作明确操作；通过平台退款，不私下重复打款。[来源四](#来源四)

每日由负责人比较平台交易与退款、本地订单与额度、平台结算与银行流水。金额不一致先拆出税额、手续费、退款、汇兑和时差，再定位缺单；所有补偿都记原因、证据、操作者与复核结果，不直接修改余额。

沙箱通过且正式审核获批后，再用平台允许的真实客户试点交易验证交付，并跟踪首笔结算；不要自刷交易。若仍在等待结算门槛，就如实记录“付款已确认、到账未验证”，不宣布全链路完成。

可复制到工单的最小模板：

```text
核对日期／负责人：
平台／环境／事件编号／业务操作编号：
订单／订阅／客户／服务期：
商品、金额、币种、税额与费用：
平台当前状态／本地状态／差异原因：
原额度流水／拟补发或冲回流水：
退款编号／结算编号／银行到账凭证：
人工操作依据／复核人／完成时间：
```

## 6. 收费前验收清单

- [ ] 主体、商品、买家地区与结算账户分别确认，保存官方回复。
- [ ] 原始请求体验签、环境隔离、重复及乱序回放通过。
- [ ] 付款失败不发放；处理失败可补偿；同一周期只发一次额度。
- [ ] 期末取消不提前停权，退款不意外触发第二笔扣款或退款。
- [ ] 部分退款、额度不足及漏通知都有人工工单和复核证据。
- [ ] 完成平台账、本地账、银行账核对；尚未到账明确标示。
