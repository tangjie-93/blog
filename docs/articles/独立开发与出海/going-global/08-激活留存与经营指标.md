# 激活、留存与经营指标：用真实任务判断产品是否成立

产品上线后，最容易看到的是访问和注册，最难确认的是“用户是否真的解决了问题”。本篇接续[搜索与本地化](./07-SEO与本地化实战.md)，从客户反馈整理器出发，建立一套表格就能维护的经营记录。

**本篇交付物**：事件字典、一份漏斗记录、一张按任务周期观察的复用表，以及下一轮只改什么的决定。本文不要求购买分析服务，数字均为教学假设。

> **视频跟练**：[`PostHog` 漏斗配置教程](https://www.youtube.com/watch?v=cMFz_xFlHaE)是旧版英语操作演示，本轮仅核对视频搜索索引。先在隔离环境用合成事件做出人数为 `4、3、2、1` 的有序漏斗，再核对重复事件不重复计人；[测试数据、操作任务与验收](./10-视频跟练与项目实操路线.md#_7-漏斗-先用合成测试事件做出一张可核对的分析)见跟练页，不上传客户原始材料。

## 1. 先定义价值，后选分析工具

### 1.1 注册和运行成功都不等于激活

对反馈整理器，可以把首次激活暂定为：

> 用户提交获授权的有效样本，得到结果，完成来源核对，并导出一份可用于工作交付的整理稿。

这个定义要在实际使用中调整。导出可能只是试着点按钮，因此它是价值的代理事件，不是用户节省时间的充分证明。早期应通过简短回访核对是否采用了结果，不能只依据埋点自我证明。

同时记录用户从开始到首次价值经历了多久，即 `Time to Value / TTV`。需要人工支持的时间也算进去；运行耗时很短，不代表用户准备数据和审核结果也很快。

### 1.2 事件字典模板

| 事件 | 何时记录 | 用来回答什么 |
| --- | --- | --- |
| `signup_completed` | 账号真正创建成功 | 注册是否完成，不代表价值达成 |
| `input_validated` | 服务端接受有效输入 | 输入格式是否阻塞 |
| `task_succeeded` | 结果校验通过且可读取 | 处理链路是否交付结果 |
| `result_exported` | 导出成功 | 是否进入后续工作，仍需回访确认 |
| `payment_completed` | 服务端确认真实交易 | 是否成交，不依赖返回页 |
| `refund_completed` | 平台确认退款完成 | 成交是否最终保留 |

同一事件应定义去重键、时间、用户或团队标识、商品版本和来源字段。不要在分析事件里放原始反馈、邮箱、支付凭据等不必要内容。身份关联、追踪与同意要求应根据地区和处理方式判断，不能认为“不放姓名就绝对匿名”。

## 2. 用同一批用户看漏斗，不把不同人拼起来

假设观察某周进入试点的 `12` 个目标团队，并给予每个团队完整的 `7` 天激活窗口。团队是统计单位，团队内多人操作需要去重。以下全部为教学示例：

| 阶段 | 同批团队数 | 相对上一阶段的比例 |
| --- | --- | --- |
| 完成注册 | `12` | 起点 |
| 输入通过校验 | `9` | `9 ÷ 12 = 75%` |
| 获得可读取结果 | `8` | `8 ÷ 9 ≈ 88.9%` |
| 完成核对并导出 | `5` | `5 ÷ 8 = 62.5%` |

整体激活比例为 `5 ÷ 12 ≈ 41.7%`。这是这批团队在规定窗口、按照本例定义得到的结果，**不是行业基准，也不是有统计把握的市场结论**。

不要用本周注册的团队数除以所有历史导出者，也不要把重复导出次数当成独立用户。分析工具通常允许设置顺序和转化窗口，使用前必须确认实际配置与自己的口径一致。

### 2.1 对每个掉落位置提出可验证解释

- 注册后没有输入：是不知道准备什么、没有数据授权，还是只是随便看看？
- 输入后没有结果：是故障、等待太久，还是用户取消？
- 有结果但不导出：是不准确、格式不合适，还是网页结果已经够用？
- 激活但不付款：是价值不足、付款失败、审批未过，还是本来就不属于付费对象？

事件告诉你哪里发生变化，访谈和错误记录帮助解释原因。单靠点击数据不能断言“用户觉得贵”。

## 3. 留存首先是任务周期，不是每天回来

### 3.1 明确起始事件和返回事件

`Amplitude` 官方留存资料区分起始事件与返回事件，来源 `S1`。本例可以采用：

- 起始：首次完成经回访确认的有效整理。
- 返回：使用另一批输入，完成下一次有效整理。
- 单位：团队，不混用成员与团队。
- 窗口：例如首次完成后的第 `7～13` 个完整日，采用约定时区，写清边界。

这里刻意不把反复打开旧结果算作新任务复用。对月度任务使用月度或自定义窗口；每月才整理一次的客户，不适合用次日回访率判断价值。

### 3.2 没走完观察窗口，不等于流失

假设某批 `5` 个已激活团队中，只有 `4` 个已走完下一轮观察窗口，另 `1` 个还未到观察期末；成熟样本里有 `2` 个再次完成任务。

本例对已成熟样本的复用比例是 `2 ÷ 4 = 50%`，并应同时披露未成熟样本 `1` 个，不能写成整批最终留存为 `50%`。未成熟样本之后可能改变结果。

`Amplitude` 的计算说明也提醒，未完成观察区间的数据不能当作零回访并直接塞入汇总，见来源 `S2`。手工表格同样需要这个约束。

### 3.3 不混淆两种留存问题

- **区间返回**：是否在指定的那段时间内完成下一次任务？
- **此后任一时间返回**：从指定时间开始到当前观察截止，是否曾经回来？

两种结果的含义不同，不能放在一张比较表里却省略口径。还应控制每批用户的观察长度，否则较早进入的人天然拥有更多返回机会。

## 4. 财务指标与行为指标要连接，但不要混算

| 指标 | 回答的问题 | 常见误用 |
| --- | --- | --- |
| 实际成交与退款 | 收了多少钱，最终退了多少 | 把支付成功截图当持续经营能力 |
| `MRR` | 活跃订阅按月规范化后的经常性收入 | 把一次性点数包、税费或全部年付现金都计入 |
| 单笔贡献 | 一笔交易扣除约定范围的变动成本还剩多少 | 忽略重试、退款和客服 |
| 客服与维护工时 | 每个有效客户需要投入多少时间 | 只看服务器费用，不计个人劳动 |
| 现金结算 | 实际到账多少，何时到账 | 把成交额等同于银行可用余额 |

`MRR` 不等于利润或现金流。具体计算还要固定折扣、取消、欠费和按量费用的政策；平台默认口径可能不同。定价与成本的可复算方法见[单位经济模型](./05-定价与单位经济模型.md)。

不要用极少样本和不稳定流失率计算漂亮的终身价值，即 `LTV`。刚起步时更实用的是记录每一笔实际收入、变动成本和投入工时，并观察真实复购。

## 5. 每轮只解决一个主要阻塞

假设本轮发现多数掉落发生在输入准备阶段。可以先提供可下载模板、明确错误列和一份合法示例，而不是同时改价格、文案、模型与注册流程。

```text
观察批次、统计单位与完整窗口：
当前最明显的阻塞：
支持该判断的事件、访谈和错误记录：
本轮唯一主要改动：
预期改善哪个具体行为：
不能恶化的护栏：错误、成本、隐私或退款。
观察截止与未成熟样本：
实际结果和其他可能影响因素：
继续、回退或进一步访谈：
```

低流量时，所谓 `A/B` 实验很可能没有足够样本给出可靠因果判断。可以先做定性可用性观察和分批改进，明确“前后变化可能受人群、渠道和时间影响”，不要把几个人的差异包装成显著提升。

**护栏不可省略**：例如激活上升，却因为放宽输入限制导致失败、处理费用或隐私风险上升，这不是单纯的成功。

## 6. 最小经营复盘节奏

### 6.1 日常看影响交付的异常

检查任务失败、积压、支付与权益不一致、异常费用和待回复求助。低频产品也需要可靠交付，不应因为日活很低就不做错误监控。

### 6.2 每周看新进入的人能否完成任务

保存同批用户的漏斗分子、分母、观察窗口、来源和产品版本。优先回访明显掉落的人，区分没有需求、不会操作和结果不可信。

### 6.3 每个自然任务周期看复用与成本

周度整理工具看下一周任务，月度整理工具看下一月。把成熟与未成熟用户分开，记录没有复用的原因：任务没发生、项目结束、转用竞品、价格不合适或质量不足。

如果还不能稳定交付一次价值，就先修激活和可靠性；如果价值能交付但任务不重复，就重新判断订阅模式；如果有复用但越卖越亏，就限制成本或调整价格，而不是只加大推广。

### 本篇验收清单

- [ ] 激活定义包含价值代理事件，并通过真实回访校验。
- [ ] 事件有去重键，用户、团队与任务统计单位不混用。
- [ ] 漏斗来自同批对象，按顺序和固定窗口观察。
- [ ] 留存已写清返回事件、时区和区间，未成熟样本单列。
- [ ] 成交、退款、经常性收入、利润和现金结算分开记录。
- [ ] 下一轮只选一个主要阻塞，并设置成本与质量护栏。
