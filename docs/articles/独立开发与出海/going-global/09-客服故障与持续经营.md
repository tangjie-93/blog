# 客服、故障与持续经营：一个人也需要可执行的运营流程

副业产品不会因为开发者正在上班、睡觉或休假就停止接受用户请求。与其承诺全天候响应，不如在开始收费前建立一套符合个人条件的支持流程。

本篇接续[激活与留存](./08-激活留存与经营指标.md)。**交付物**是一页支持政策、一份故障处理手册、一次恢复演练记录，以及继续经营或有序退出的判断。客户反馈整理器仍是教学案例，以下响应时间都是自定目标示例，不是法定义务或行业标准。

> **视频跟练**：[`Supabase` 备份恢复到新项目的演示](https://www.youtube.com/watch?v=het8VeSoBZw)提供英语第三方操作参考，本轮只核对搜索简介。仅在独立测试环境使用合成数据，恢复后检查权限、文件与配置，不把数据库表恢复视为全站恢复；[任务与覆盖风险提示](./10-视频跟练与项目实操路线.md#_8-恢复-看到表回来-不代表整个产品已恢复)见跟练页。

## 1. 把支持承诺写成自己能做到的样子

### 1.1 先定义服务范围

区分“用户能在任何时候提交问题”和“开发者能立即回复”。产品可以提供全天可用的联系入口，但不应据此宣传全天人工在线。

```text
支持入口与备用联系渠道：
支持语言、工作日与时区：
常规首次响应目标，不等于解决时限：
故障公告与下一次更新时间的发布位置：
退款、删除与账户问题的处理方式：
不提供的服务：定制开发、远程操作或其他事项。
超出能力时：暂停新任务、停止试用或限制销售的规则。
```

英文说明要把时区和工作日写清，而不是只写“今天内回复”。不要承诺“所有问题在一天内解决”，因为支付争议、外部服务中断和数据恢复不完全由你控制。

### 1.2 把重复问题变成产品改进

每次求助记录用户想完成什么、在哪一步受阻、是否影响交付。连续出现“文件怎么准备”，优先改输入模板和报错，而不是只添加一篇很长的常见问题。

客服记录也是需求证据，但不代表每个请求都要实现。对个别客户的定制需求，明确是否属于额外服务、费用、交付期和支持边界，避免一次小额购买变成无限外包。

## 2. 简单分级，让重要问题先被处理

| 类别 | 示例 | 优先动作 |
| --- | --- | --- |
| 数据与权限风险 | 怀疑用户看到他人反馈 | 限制相关访问或暂停功能，保护证据并启动调查 |
| 钱与权益不一致 | 已付款但没有额度，重复扣减 | 停止相关自动化，核对支付与权益流水 |
| 核心交付受阻 | 任务长期积压、结果不可读取 | 暂停新增负载，恢复已有任务或按政策补偿 |
| 一般使用困难 | 不清楚模板字段、导出格式不合适 | 解释并记录可重复的改进事项 |
| 功能建议 | 想增加外部集成 | 纳入需求研究，不承诺立即交付 |

不需要一开始引入复杂工单系统，一张访问受控的记录表就能起步。不要把客户数据、支付截图或日志直接粘贴进公开问题区。

### 2.1 首次回复示例

```text
已收到你关于任务 [编号] 无法完成的问题。
目前确认：该任务没有生成可用结果；是否影响其他任务仍在核对。
请不要重复付款，也不要发送完整反馈文件或支付凭据。
你可以提供发生时间、页面错误文字和已脱敏的截图。
我们会在 [带时区的时间] 前更新进展；这不是完成修复的保证。
额度或退款处理将按公布的政策和核对结果另行说明。
```

回复应区分“已确认”“正在核对”和“暂时未知”。不要为了安抚对方，未经调查就写“数据绝对安全”或“肯定没有扣费”。

## 3. 故障时先控制影响，再深挖原因

`Google SRE` 故障响应资料区分恢复服务、协调行动和沟通进展，见来源 `S1`。个人开发者不必复制指挥官编制，但可以把角色转为一份顺序明确的检查表。

### 3.1 一页故障手册

1. **确认影响**：哪条用户路径、哪些时间和任务受影响？不要先假定所有故障都来自最近发布。
2. **控制扩散**：必要时暂停高成本任务、新销售或相关功能；不盲目让用户反复重试。
3. **保留必要证据**：记录版本、错误类型、任务和交易标识，避免复制不必要的原始敏感内容。
4. **选择恢复动作**：回滚兼容版本、暂停执行器、切换已验证的备用路径，或明确进入维护。
5. **更新用户**：说明已知影响、临时办法和下次更新时间；原因不明就如实写明。
6. **核对恢复**：用受控样本确认核心路径，排查重复处理、漏发权益和未完成任务。
7. **处理后续**：按照政策补偿，完成内部复盘和必要的专业咨询。

数据库变更不一定能靠代码回滚解决。支付平台和自己的数据库也不能随意各自恢复到不同时间，然后假定账目一致；必须重新核对外部事实。

### 3.2 示例：处理服务超时，队列开始堆积

先限制新任务，保留已有任务标识。查看外部服务是否可能继续完成工作，避免把超时任务全部自动重跑。恢复后逐项确定哪些已完成、哪些可安全重试、哪些需要返还额度。

对用户说“处理延迟，正在核对任务与额度”，比把所有任务改成成功或承诺立即退款更诚实。是否需要退款、返还额度或重新交付，要遵循事前政策及适用规则。

## 4. 备份恢复要覆盖经营事实

### 4.1 不只备份业务数据库

列出任务、上传文件、支付事件、额度流水、必要配置和域名控制权分别依赖什么。密钥与恢复凭据应使用适合的安全保管方式，不能为了备份方便放进公开仓库。

`Supabase` 文档明确数据库备份不包含对象存储文件，见来源 `S3`。即便不用它，也要检查供应商的备份范围、保留期限、删除行为及恢复限制。

### 4.2 在隔离环境做演练

1. 使用不含真实敏感内容的样本准备恢复目标。
2. 恢复数据库、对象和必要配置，保持出站邮件、正式支付及后台消费关闭。
3. 检查用户隔离、来源对应、历史结果和额度余额。
4. 模拟恢复点之后的支付事件，确认重放不会重复发放权益。
5. 记录花了多久、丢失哪些时间范围的数据、哪里依赖手动操作。

恢复旧备份可能让已删除内容重新出现。正式恢复时需重新应用删除记录和保留策略，限制恢复环境访问，并按实际能力披露备份清理周期。

## 5. 复盘要产生可验证的动作

`Google SRE` 的无责复盘原则强调，复盘不止于写报告，还要形成可跟踪的改进，见来源 `S2`。个人开发者也不应把结论写成“下次细心点”。

```text
事件、开始时间、发现时间与恢复时间：
已确认的用户与资金影响；仍未知的范围：
按时间排序的观察与操作：
直接触发条件，以及系统为什么允许它扩大：
哪些保护有效，哪些缺失：
本次补偿、通知与对账情况：
改进动作、负责人、完成时间与验收方法：
已关闭动作和仍未关闭的风险：
```

例如“增加任务超时后的外部状态核对，并用延迟回调样本验证不会重复扣额度”，比“优化稳定性”具体。只有自己一名开发者时，也写日期和验收方法，防止报告变成永久搁置的待办。

涉及疑似个人数据泄露时，应查适用法律、合同和平台要求，必要时及时寻求专业帮助。技术恢复不等于事件责任已经结束，不能照搬一个全球通用的通知期限。

## 6. 用个人时间和责任判断是否继续经营

### 6.1 每月问四个问题

- 用户是否还在重复完成真实任务，而不只是领取免费额度？
- 扣除可追踪成本和合理的个人工时后，这个模式是否值得继续？
- 自己离线时，系统能否限制损失，用户能否获得真实状态？
- 收款、数据、域名与依赖服务是否仍符合当前条件？

高收入截图不能替代这些问题。也要检查雇佣合同、利益冲突和知识产权边界，不用本职工作的保密资料、账号或未授权成果经营副业。

### 6.2 暂停或关闭时，要完成交接而不是直接关站

1. 停止新销售，明确何时停止新增任务。
2. 通过适当渠道通知用户，解释导出、退款与联系办法。
3. 在支付平台确认续费已按计划停止，保留可核对记录。
4. 依合同、商品承诺和适用规则处理剩余额度、年费与争议。
5. 提供合理的数据导出与删除流程；依法保留必须留存的会计或争议记录。
6. 清理凭据和依赖，但不要过早删除仍需处理售后的渠道。

不要在不了解长期责任时卖“终身无限使用”。退出方案从一开始就是定价和商品承诺的一部分，而不是倒闭前才补上的文案。

### 本篇验收清单

- [ ] 支持入口、语言、时区和响应目标真实可执行。
- [ ] 数据风险、资金问题和普通建议有不同优先级。
- [ ] 能暂停新增工作，有故障手册与备用沟通渠道。
- [ ] 已在隔离环境恢复，并防止真实交易或通知被重放。
- [ ] 复盘动作有时间、验收方法和关闭记录。
- [ ] 取消续费、用户导出、退款和数据清理有退出方案。
